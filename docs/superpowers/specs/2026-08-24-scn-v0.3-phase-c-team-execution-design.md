# SCN v0.3 Phase C — Agent-Team Execution Design

**Status:** Approved · **Date:** 2026-08-24 · **Scope of this doc:** how Phase C is executed, not what it builds

## Relationship to the source plan

Phase C's feature scope (tasks C1.1–C6.1) is already fully specified in `docs/superpowers/plans/2026-08-20-scn-v0.3-workspace.md` §4, including the pinned design decisions this doc does not revisit:

- **DD-3** — `pickBaseline(scenarios)`: scenario named "Baseline" (case/whitespace-insensitive), else oldest by `createdAt`. One pure function, one call site.
- **DD-7** — "Save run as scenario" rides `result_cache`: create scenario with the run's inputs snapshot, trigger solve, cache hit returns instantly. Zero backend change.
- **Band semantics** — `lib/bands.ts`'s `computeBandCoverage` stays exclusive (half-open buckets, Round 3 decision); the Reports tab computes a **cumulative rollup** on top of the exclusive bins at the Reports layer only. `bands.ts` and the map's band coloring are untouched.

This doc's only job is deciding **how the 5-role agent team executes those 6 tasks**, replacing Phase A/B's `subagent-driven-development` (one implementer + reviewer per task, strictly sequential) with parallel role-based dispatch per the user's standing instruction: plan the task breakdown so execution maximizes real team parallelism.

## Why Phase C parallelizes well

Unlike Phase B (where every fast-follow model touched shared solver/precheck/import infrastructure and had to be sequenced to avoid the recurring per-model-gating bug class), Phase C's p-median-us pilot tasks (C1.1–C5.1) touch almost entirely disjoint new files:

- New output grid tab components (C1.1) — frontend, new files
- New `pickBaseline.ts` + `ReportsTab.tsx` (C2.1) — frontend, new files
- Export-service extension for output entities (C1.1's backend half) — backend, extends an existing service but a different code path than anything else in this phase touches
- Clipboard spike (C4.1) — pure research, no production files
- Solve-history "save as scenario" (C5.1) — frontend, touches the existing solve-history stepper component, unrelated to the new tabs

The only real sequencing constraints are: C3.1 needs C2.1's `ReportsTab.tsx` to exist first (it extends that same file), C4.2 needs C4.1's decision, and C6.1 (fast-follow to `transport-coal`/`two-echelon-gold-au`/`p-median-brazil`) needs the p-median-us pilot (C1.1–C3.1) proven first — same pilot-then-fast-follow shape Phase B already validated.

## Team assignment

Explicitly no work this phase for:
- **`solver-engineer`** — Phase C reads existing result envelopes and writes nothing server-side to `solve.py`/`merge_inputs.py` (confirmed by the source plan's own rollback table: "Phase C reads existing result envelopes; writes nothing").
- **`devops-engineer`** — no CI/infra changes anticipated.

This is correct team usage, not underuse — a role sits out a phase when the phase genuinely has nothing for it, rather than being given manufactured work.

### Wave 1 — parallel, dispatched together (no shared files, no ordering dependency)

| Task | Role | Files |
|---|---|---|
| C1.1 backend half | `backend-engineer` | export-service extension for output entities |
| C1.1 frontend half | `frontend-engineer` (instance A) | new output grid tab components |
| C2.1 | `frontend-engineer` (instance B) | `lib/pickBaseline.ts`, `ReportsTab.tsx` (new) |
| C4.1 | `frontend-engineer` (instance C) | spike — decision note only, no production code |
| C5.1 | `frontend-engineer` (instance D) | solve-history stepper's "Save as scenario" |

`qa-sdet` follows each Wave 1 piece as it lands (report-math unit tests for C2.1's deltas/cumulative-rollup monotonicity, envelope-to-grid mapping tests for C1.1) rather than batching all test-writing to the end — this mirrors Phase B's "task review runs right after its own task" cadence, just fanned across roles instead of serialized.

### Wave 2 — sequential dependents

| Task | Role | Depends on |
|---|---|---|
| C3.1 | `frontend-engineer` | C2.1 (`ReportsTab.tsx` must exist) |
| C4.2 | `frontend-engineer` | C4.1 (spike decision) |

### Wave 3 — fast-follow (mirrors Phase B's pilot→fast-follow shape)

| Task | Role | Depends on |
|---|---|---|
| C6.1 | `frontend-engineer` (+ `backend-engineer` if the export-entity extension needs per-model variants) | C1.1 + C2.1 + C3.1 proven on p-median-us |

## Review discipline carried forward from SDD (kept, not lowered)

Even though dispatch is now parallel/role-based rather than the strict one-task-at-a-time SDD loop, these habits carry forward unchanged:
- Each task still gets its own real commit and its own task-scoped review before being considered done.
- `e2e_accuracy.py` stays the sacred gate — re-run directly if any task ever touches solver output shape (none of C1.1–C6.1 currently should).
- No task is marked complete without its own test coverage landing alongside it.
- A progress ledger continues to track what's done, mirroring Phase A/B's `.superpowers/sdd/progress.md` pattern (adapted for parallel waves rather than a strictly sequential list).
- Model-integration-precheck.md's Gate 1 checklist still applies to C6.1's fast-follow (any new per-model registration point).

## What this doc deliberately does not cover

- Phase C's actual UI/data design (cost breakdown table layout, which fields go in which grid) — already specified in the source plan and the wireframe it references (screens 1a·1–1a·5).
- Whether to revisit DD-3/DD-7/band-semantics — explicitly out of scope per the "light brainstorm" decision; those stay as the source plan already pinned them.
