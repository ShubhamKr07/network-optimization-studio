# Bundle 6.1 — Map legend unify/realign + Distances table merge

**Date:** 2026-09-05
**Status:** Design — written-spec review resolved (see resolutions log)

## Written-spec review — resolutions (2026-09-05)

Seven findings; all resolved inline:

1. **[P1] Demand ramp must encode SIZE, not shade — and is Input-only.** The maps
   encode demand by radius, not color intensity (Input: discrete `QUINTILE_RADII`;
   Output: a DIFFERENT continuous 3..8 scale, `NetworkMap.tsx:293-305`). A shared
   opacity ramp would mislead on Input and be wrong on Output. **Resolved
   (item 1):** the demand group is **Input-map only**; it renders equal outer
   grid cells (for alignment) each containing a **centered circle of the real
   quintile radius** (`QUINTILE_RADII[bucket]`) — size-encoding, matching the
   map. It renders **only `scale.usedBuckets`** (not always five — the earlier
   "five-step" wording was contradictory; fixed). The Output legend has NO demand
   group — just a single Customer marker — so the Input/Output scale mismatch
   never surfaces.
2. **[P1] "All models" omitted two-echelon's separate component (user chose:
   include it).** two-echelon routes its Distances entry to `LegDistancesTab`
   (2-leg, leg-type column), NOT `DistancesTab`. **Resolved (item 2/T2):** scope
   is `DistancesTab` (p-median-us base+overrides merge; p-median-brazil
   override-only restyle) **AND** `LegDistancesTab` (two-echelon — restyle to the
   Customers-tab look, keeping its 2-leg/leg-type structure; no base matrix
   exists for it). Transport's `LaneCostsTab` is **explicitly out of scope**.
3. **[P1] Merge could hide overrides on inactive/excluded pairs.** Filtering
   reference pairs by inactive/excluded and appending only overrides absent from
   the base matrix would drop an override on a base pair whose warehouse is
   inactive / customer excluded (its reference row filtered out, but its key is
   in the base matrix so not appended) — the user could no longer see/clear it.
   **Resolved (item 2):** build the complete base-key lookup BEFORE view
   filtering; **any pair carrying an override is always shown**, regardless of
   the inactive/excluded view filter. Preserves today's ability to inspect/clear
   every persisted override.
4. **[P2] Blank/clear/validation/changed-row/drafts semantics defined.** See
   item 2's "Override cell semantics" — explicit transitions + 4 mandated tests.
5. **[P2] "City if available" isn't derivable here — dropped.** `ReferenceDistancePair`
   carries only ids/codes/distance; DistancesTab has no city metadata (only id
   arrays + `displayCodeById`). Rather than thread a new label prop + a
   `Workspace.tsx` call-site change, **From/To show id/`displayCode` only**
   (city removed from the columns) — keeps the change within DistancesTab/
   LegDistancesTab.
6. **[P2] Loading/failure behavior defined.** The merged table must NOT silently
   mark every override `Base = N/A` while the reference matrix is merely loading
   or failed. See item 2's "Reference load/error states."
7. **[P2] Output legend must match actually-rendered marker states.** Output
   markers come from `NetworkMap.getStatus`, which checks `openWarehouseIds`
   BEFORE `warehouseStatuses` — so a forced-open facility in a solved result
   renders as `open`, not `forced_open`. **Resolved (item 1):** the Output legend
   is defined from the states `getStatus` actually produces (include **Open**;
   drop **Forced-Open** as a separate Output entry since it resolves to Open
   post-solve) — the plan reads `getStatus` precisely and covers the
   marker→legend mapping in `NetworkMap.test.tsx`, not by asserting labels in
   isolation.

## Goal

Two UI refinements: (1) make the map legend better sized/aligned by unifying the
Input and Output legends into one shared component with a content-fit aligned
grid and a graduated demand ramp; (2) merge the Distances tab's separate base
(reference) and user-override tables into one Customers-tab-styled table.

## Scope / non-goals

- **Frontend-only.** No backend/API change — the reference-distances endpoint
  and `distanceOverrides` already exist.
- Light theme only; tokens from the theme system; no `Studio.tsx` /
  `.studio-lab` / `--arc-*`. Never hand-edit generated code (none touched).

## Decisions (locked via Q&A)

- Demand buckets → a **graduated ramp in an aligned grid** (not variable bubbles).
- **One shared legend component**, content-fit + aligned grid (drop the fixed
  `w-[220px]` from Bundle 6).
- Distances merge model: **base rows read-only + a merged "override" column**
  (not every-cell-editable).
- Distances scope: **restyle all** models' Distances tab to the Customers-tab
  look; base rows appear only for p-median-us (the only model with a base
  matrix).

## Item 1 — Map legend: unify + realign

**Files:** `components/workspace/map/MapLegend.tsx` (becomes the single shared
legend); `components/NetworkMap.tsx` (drop its hand-duplicated inline legend,
render the shared component); `components/workspace/tabs/InputMapTab.tsx` /
`OutputMapTab.tsx` (call sites, if props change); `map/types.ts`/`EntityMarkers`
(read `QUINTILE_RADII`/thresholds for the ramp). Tests:
`MapLegend.test.tsx`, `NetworkMap.test.tsx`.

**Problem (evaluation):** today there are two legend implementations — `MapLegend`
(Input, overlay bottom-left) and a hand-duplicated inline legend in `NetworkMap`
(Output, bottom-right). Both are pinned to a fixed `w-[220px]` + `flex-wrap`
(Bundle 6 parity patch), which produces dead space or ragged 2-row wrapping; and
the Input demand group renders variable-diameter bubbles on a wrap row, so
bubbles don't share a baseline and labels misalign.

**Design:**
- **Single shared component.** `MapLegend` is the one legend. `NetworkMap`
  deletes its inline legend markup and renders `<MapLegend …>` with the groups
  the Output map needs. The component renders a **prop-selected set of legend
  groups**, each a titled sub-section:
  - `status` group — warehouse-role status markers. **Input:** Potential /
    Fixed-Open / Inactive. **Output (resolution #7):** defined from the states
    `NetworkMap.getStatus` actually renders — **Open** (solved-open),
    **Potential** (candidate not opened), **Customer**, and **Mine** when the
    dataset has one. Drop "Forced-Open" as a separate Output entry (a forced-open
    facility in a solved result resolves to `open` via getStatus's
    `openWarehouseIds`-first precedence). The plan reads getStatus precisely and
    asserts the marker→legend mapping in `NetworkMap.test.tsx`. Driven by
    prop flags so one component covers both maps' marker sets without divergence.
  - `demand` group — the size ramp (below). **Input-map only** (resolution #1);
    Output shows only the single Customer marker, no demand ramp.
  - `routes` group — the distance-band color chips (Output only, when a result
    with `showRoutes` exists) — moved out of NetworkMap into the shared
    component.
  - optional `hint` line (Output's existing hint text).
- **Content-fit box + aligned grid.** Drop the fixed `w-[220px]`. Use
  `w-fit max-w-[260px]` and lay each group as a **2-column grid**
  (`grid grid-cols-[auto_1fr] gap-x-2 gap-y-1 items-center`): swatch column
  (fixed width, centered) | label column (left, `text-xs`), with a small group
  header (`text-[10px] uppercase tracking-wide text-muted-foreground`). Groups
  stack with a divider. Consistent baselines, no ragged wrap.
- **Demand size ramp (Input only, resolution #1).** Replace the variable-bubble
  wrap row with an **aligned grid where each row is one occupied bucket**: an
  equal-size outer cell (fixed, e.g. `w-6 h-6`, for column alignment) containing
  a **centered circle drawn at the real quintile radius** (`QUINTILE_RADII[bucket]`,
  the same value `EntityMarkers`/`customerBubbleSvg` use) in the demand tone at
  constant fill — so the legend encodes demand by **size**, exactly as the map
  does, with baseline-aligned rows. The `bucketLabel` range sits in the label
  column. Render **only `scale.usedBuckets`** (one row per occupied bucket — not
  always five). Preserve `legend-demand-bucket-<bucket>` (one per shown bucket)
  and `legend-status-<status>` testids.
- **Placement unchanged:** Input overlay bottom-left, Output overlay
  bottom-right (or both bottom-left — keep current corners). `pointer-events-none`
  retained.
- **Parity is now "same component/style," not "same pixel width."** The Bundle 6
  `w-[220px]`/`flex-wrap` on both legends is removed. Update any test that
  asserted the 220px width or the old bubble markup.

## Item 2 — Distances tab: merge base + overrides into one Customers-styled table

**Files:** `components/workspace/tabs/DistancesTab.tsx` (+ `DistancesTab.test.tsx`);
`components/workspace/tabs/LegDistancesTab.tsx` (+ `LegDistancesTab.test.tsx`) —
two-echelon, per resolution #2. Reference styling:
`components/tables/CustomerTable.tsx` / `components/workspace/tabs/CustomersTab.tsx`.
**Out of scope:** transport's `LaneCostsTab` (a structurally different table).
`LegDistancesTab` has no base matrix — it's the Customers-tab **restyle** only
(one table, its existing 2-leg/leg-type column + override cells kept), NOT a
base-merge.

**Problem:** the Distances tab shows two stacked tables — a read-only paginated
"Base distances (reference)" section above a separately-paginated editable
`distanceOverrides` table. The user wants them in ONE table that looks like the
Customers tab.

**Design:**
- **One table** (shadcn `Table`/`TableHeader`/`TableRow`/`TableHead`/`TableCell`,
  matching CustomerTable's look) replacing both current sections. Columns:
  - **From** — `displayCode`/id (via `displayCodeById`), the unknown-id warning
    icon kept. (No city — resolution #5: DistancesTab has no city metadata and
    threading one would require a new prop + a Workspace.tsx call-site change,
    out of this bundle's frontend-in-DistancesTab scope.)
  - **To** — `displayCode`/id, warning icon kept.
  - **Base distance** — read-only, from the reference matrix; `"—"` only when the
    pair genuinely has no base (a user-created added-entity pair). NOT "—" while
    the reference query is loading/errored (see "Reference load/error states").
  - **Override** — an editable `Input` + a clear/reset affordance. Semantics below.
    The `estimated` badge stays.
- **Row set (p-median-us) — overrides always visible (resolution #3):**
  1. Build the COMPLETE base-key set from ALL reference pairs (before any view
     filter).
  2. Enumerate the base reference pairs, applying the From/To + inactive/excluded
     view filter — BUT a base pair that carries a `distanceOverride` is **kept
     visible even if the inactive/excluded filter would hide it** (so a persisted
     override on an inactive-warehouse / excluded-customer pair can always be
     inspected and cleared). Join each shown base pair to its override by
     `pairKey`.
  3. **Append** any `distanceOverride` whose pair key is NOT in the complete base
     key set (user-created added-entity pairs) as extra rows, Base = "—".
  One table, base + overrides + added together; one pager; From/To filters over
  this merged set.
- **Override cell semantics (resolution #4):**
  - Typing a valid positive number creates/updates the override for that pair
    (live, via the existing `onChange` into `distanceOverrides`); the row shows
    the CustomerTable "changed" highlight when the override differs from the
    saved value (compared on the merged pair, **including presence/absence** — a
    just-cleared-but-unsaved override still highlights as changed until Save).
  - A non-empty invalid draft (`≤0`/NaN) shows an inline error and does NOT
    commit (mirrors the current `updateDistance` guard).
  - **Clearing** an override is done by the explicit clear/reset control (the
    repurposed `X`), which removes the entry from `distanceOverrides` AND deletes
    its `drafts` map entry (the base row stays mounted, so a stale draft would
    otherwise linger); an empty input alone does NOT silently drop a saved
    override.
  - **Mandated tests:** add an override to a base row; edit it; clear it (row
    reverts to base, no override); clear a PREVIOUSLY-SAVED override and confirm
    the row stays highlighted-as-changed until Save.
- **Reference load/error states (resolution #6):** while `referenceQuery` is
  loading, show a loading indicator for the base rows (override rows still
  editable); on error, show an error banner AND keep the override rows editable,
  with Base shown as "unavailable" (NOT "—"), so the user never mistakes a
  transient reference outage for "this pair has no base." Only a pair whose key
  is genuinely absent from a SUCCESSFULLY-loaded base matrix shows Base = "—".
- **Row set (p-median-brazil):** no base matrix (`referenceCapable` false), so
  the `DistancesTab` shows only the user-created `distanceOverride` rows (Base
  column "—"), restyled to the same Customers-tab look. No base rows to
  enumerate.
- **two-echelon (`LegDistancesTab`, resolution #2):** a **restyle only** — keep
  its existing 2-leg / leg-type column + override cells + interactions; re-skin
  the table to the Customers-tab look (shadcn `Table`, inline cells, same
  changed-row/override semantics as above where they apply). No base matrix, no
  base-merge. Its own tests updated for the restyle.
- **Pagination + filters:** keep the 50/page pager and the live From/To filters
  (now over the single merged, filtered row set — one pager, not two). The
  `focusEntityId` jump (Bundle 5/6 one-shot page selection) retargets the single
  table. Clamp-on-shrink behavior retained.
- **Add-row** (user-created pair) stays available (the existing "+ Add row"
  flow), appending an added-entity override row.
- **Import/export** toolbar unchanged (still `entity="distances"`).
- Preserve `row-distance-*` / `row-reference-distance-*` (or consolidate to one
  `row-distance-*` scheme — update tests accordingly) and all filter/pager
  testids.
