# SCN v0.3, Phase 3.2 — Table Columns, Input Map, Removals, Renames

**Status:** Approved · **Date:** 2026-08-26 · **Scope:** Workspace shell + its input/output tabs, across p-median-us, transport-coal, two-echelon-gold-au (Brazil explicitly excluded per its own pre-existing boundary — no dataset-browsing tables exist for it, and this phase isn't building them).

## Summary of changes

1. Add City/State (split from the current merged column)/Latitude/Longitude/Zip-or-postcode columns to the four shared entity tables (`WarehouseTable`, `CustomerTable`, `MineTable`, `StationTable`).
2. Real postal-code data: one-time reverse-geocode script, US zip for p-median-us + transport-coal, Australian postcodes for two-echelon.
3. New "Input Map" tab per model (p-median-us, transport-coal, two-echelon) showing current facilities/customers as pins pre-solve, with click-to-place feeding the existing add-forms.
4. Remove: Reports tab (Workspace), `Compare.tsx` page, `POST /scenarios/compare` backend route, "Reset to Baseline" everywhere (UI + backend).
5. Rename: "Cost Summary" → "Solution Summary"; app title "Supply Chain Design"/"Prof. Michael Watson" → "SCND Optimization Studio"/"By Prof. Michael Watson" (Phase 3.1 already put this branding in 4 places — same 4 get updated again).
6. New automated tab-coverage tests (p-median-us, transport-coal, two-echelon) + a live manual QA pass exercising every tab, done at the end.

## 1. Table columns

Confirmed live: `WarehouseTable.tsx`, `CustomerTable.tsx`, `MineTable.tsx`, `StationTable.tsx` all currently render `ID | City, State | [entity-specific column] | Status`, with `City, State` as one merged cell and no lat/lng column at all — despite `lat`/`lng` already present on every row's upstream type (`WarehouseCandidate`, `Customer`, and their Mine/Station equivalents). New column order: `ID | City | State | Latitude | Longitude | Zip | [entity-specific] | Status` (Warehouses keeps its existing conditional Capacity column in the entity-specific slot; Customers/Mines/Stations keep their existing Demand/Capacity-override columns there, unchanged).

- City/State split and Latitude/Longitude: no new plumbing — the data already flows in, only the local `*Row` interfaces (currently narrowed to `{id, city, state}`) and the rendered `<TableHead>`/`<TableCell>` need widening.
- Zip/postcode: new field, not in any dataset today. Added as `zip?: string` on the relevant row types. Column renders only when at least one row in the current dataset actually has a `zip` value (same conditional pattern the Warehouses table already uses for Capacity) — so two-echelon's Australian rows get an "Australian postcode" column once that data exists, Brazil (no tables) is structurally unaffected, and nothing needs a per-model `if (modelId === ...)` branch.
- Latitude/Longitude/Zip are display-only for **base dataset** rows (immutable per this repo's DD-1 rule — base dataset JSON is maintainer-authored content, not user-editable at runtime). They're already editable for **added** rows via the existing add-forms' Lat/Lng number inputs (unchanged, still typeable) — Section 3 adds a second way to fill those same inputs (click-to-place), not a replacement.

## 2. Postal-code sourcing

New one-time script (`scripts/src/fetch-postal-codes.ts` or a Python equivalent alongside the existing `scripts/src/migrate-scenario-inputs.ts` precedent — exact language decided during plan-writing based on which is easier to run against the JSON files directly) that:

- Reads each target dataset's warehouses/customers (p-median-us), mines/stations (transport-coal), refineries/customers (two-echelon).
- For each row, reverse-geocodes `lat`/`lng` via Nominatim (`https://nominatim.openstreetmap.org/reverse?lat=...&lon=...&format=json`, confirmed reachable from this environment) with a `User-Agent` header and a 1 request/second delay (Nominatim's usage policy) — total runtime a few minutes for the ~240 combined rows across the three models. Resumable: re-running the script skips rows that already have a `zip` rather than starting over, so a mid-run throttle/failure doesn't force a full restart.
- Extracts `address.postcode` from the response, writes it back as a new `zip` field directly into the base dataset JSON files (`solvers/p-median-us/dataset/{warehouses,customers}.json`, `solvers/transport-coal/dataset/{mines,stations}.json`, `solvers/two-echelon-gold-au/dataset/{refineries,customers}.json`).
- Logs (not silently swallows) any row where the API returns no postcode — a handful of misses are expected and acceptable (rural/remote coordinates); the column simply shows nothing for those rows, doesn't block the rest.

This is authored, one-time dataset content — the same category of change as the original C1.1 dataset extraction, not a runtime scenario edit, so it doesn't conflict with DD-1.

### Zip plumbing — three layers, all required, verified against the real code

Adding `zip` to the raw dataset JSON is not sufficient on its own — confirmed by reading the actual loader chain, there are three independent places that silently drop unrecognized fields before they'd ever reach the UI:

1. **`lib/dataset-schema/src/index.ts`'s Zod entity schemas** (`WarehouseEntry`, `CustomerEntry`, `MineEntry`, `StationEntry`, `RefineryEntry` — `GoldMineEntry`/`GoldCustomerEntry` inherit from these) have no `zip` field today. `validatePackage()` calls `schema.parse(raw)` on every load, and Zod's default (non-strict, non-passthrough) behavior strips unknown keys — so `zip` never survives even the first load unless these schemas declare `zip: z.string().optional()`.
2. **`transportCoalDataset.ts`/`twoEchelonDataset.ts`** — confirmed by reading both files: they don't cast raw JSON, they explicitly rebuild each row via `.map((m) => ({id: m.id, city: m.city, state: m.state, lat: m.lat, lng: m.lng, ...}))` with a fixed field list that doesn't include `zip`. Both the `MineEntry`/`StationEntry`/`RefineryEntry`/`GoldCustomerEntry` local interfaces in these files *and* the `.map()` bodies need `zip` added, or it's silently dropped a second time even after fix #1.
3. **`version.json`'s `sha256`** (`solvers/<model>/dataset/version.json`) is a real, pytest-enforced drift gate — confirmed via `test_datasets.py`, which recomputes each package's sha256 over its raw dataset file bytes and asserts it matches the stored value. Editing `warehouses.json`/`customers.json`/`mines.json`/`stations.json`/`refineries.json` to add `zip` changes those bytes; every affected package's `version.json` needs its `sha256` (and its `version` integer, for consistency with `jobRunner.ts`'s cache-hash usage, even though `zip` being display-only means stale cache content would still be numerically correct) recomputed and committed in the same change, or `test_datasets.py` fails outright.

**p-median-us is exempt from all three.** Verified: `artifacts/api-server/src/data/dataset.ts` reads its JSON files directly (`readFileSync`/`JSON.parse`, its own local `WarehouseCandidate`/`Customer` interfaces, no `validatePackage()` call, no Zod schema in the path) and casts with `as WarehouseCandidate[]` — no field-list mapping to update. Only the OpenAPI-facing `WarehouseCandidate`/`Customer` schemas (Section "Schema/type plumbing" below) need `zip` for p-median-us; transport-coal and two-echelon need all three layers above *in addition* to the OpenAPI schema change.

**Schema/type plumbing (OpenAPI-facing, all four models):** `zip` added to `WarehouseCandidate`/`Customer` in `openapi.yaml` as an optional string, codegen regenerated. `solve.py` doesn't need to read `zip` at all (it's display-only, never a solver input) — this addition is purely so the field survives the dataset-loading → API response path uncorrupted for every model, on top of the three dataset-package-internal layers above for transport-coal/two-echelon specifically.

## 3. Input Map + click-to-place

New tab, one per applicable model (p-median-us, transport-coal, two-echelon), added to `inputEntriesForModel()`'s per-model arrays alongside the existing Customers/Warehouses/Distances/etc. entries. Not built for Brazil (no dataset-browsing tables to place pins from).

**Component:** a new, deliberately lightweight `InputMapTab.tsx` — not a mode flag bolted onto `NetworkMap.tsx` (591 lines, already coupled to solve-result edges/bands/routes; adding pre-solve concerns there risks destabilizing the Output Map). Shares `lib/mapBounds.ts` (already model-agnostic, 37 lines) for country bounds/center/zoom, and the same Leaflet `MapContainer`/marker/legend conventions `NetworkMap.tsx` already established, but renders only: base dataset pins + added-entity pins, colored by current status (reusing the existing Potential/Fixed-Open/Inactive-style legend convention), no edges, no bands, no routes.

**Which entity type a click adds — resolved.** Every applicable model has ≥2 addable roles (p-median-us: warehouse/customer; transport-coal: mine/station; two-echelon: refinery/customer), and a bare `(lat, lng)` click doesn't say which. Fix: `InputMapTab` renders a small segmented toggle above the map — "Placing: Warehouse | Customer" (or the model's equivalent pair) — reusing the same `.seg`-style button-group pattern already used for warehouse status pickers elsewhere in this codebase, not a new UI primitive. The toggle's current selection is passed through: `onPlacePoint: (lat: number, lng: number, kind: string) => void`, where `kind` is one of the model's own existing entity ids (`"warehouses"`/`"customers"`, `"mines"`/`"stations"`, `"refineries"`/`"customers"`) — the same strings `inputEntriesForModel()` already uses, so `Workspace.tsx`'s dispatch to the right add-form is a direct lookup, not a new mapping table.

**Click-to-place, with an explicit confirm step (fix for the misclick risk):** a map click does not immediately open the add-form. It drops a **draft marker** at the clicked point — visually distinct from committed pins (dashed outline / different color, matching the existing status-color legend convention but clearly marked "draft") — with a small popup anchored to it showing the exact lat/lng, the currently-selected placement kind (from the toggle above), and two actions: **Confirm** and **Cancel**. Cancel removes the draft marker, no state changes anywhere. Confirm calls `onPlacePoint(lat, lng, kind)`; `Workspace.tsx` opens the relevant add-form tab (or a shared lightweight dialog) with `newLat`/`newLng` pre-populated, then reuses the exact same `onAddedWarehousesChange`-style callback the form already calls on submit — no new data path, no new backend contract. This gives a misclick two independent recovery points: Cancel on the draft marker itself, or simply not submitting the pre-filled add-form.

The numeric Lat/Lng inputs in each add-form stay as-is and remain independently editable — map-click is an additional way to fill them, not a replacement (matches the earlier clarification: both, not one instead of the other).

**Missing-distances follow-through — corrected for the real save/precheck timing.** Verified: `usePrecheckScenario` (`Workspace.tsx`) is a server query keyed to the *persisted* scenario, invalidated only after an explicit Save (confirmed at the two `invalidateQueries({queryKey: getPrecheckScenarioQueryKey(...)})` call sites). A row added via Confirm only exists in unsaved `localInputs` at that moment — there is no real precheck count to report yet, so the original "toast fires immediately with a distance count" design was wrong as written. Corrected two-step flow:
1. **On Confirm** (row added to unsaved local state): a toast names the new entity and says it's unsaved — e.g. "Added WH27 to this scenario — Save to check for missing distances." No count claimed yet.
2. **On the next successful Save** (existing Save flow, already triggers the precheck invalidation above): if the refetched precheck result has errors referencing the newly added entity's id, a second toast reports the real count and links to the correct tab — reusing `precheckDisplay.ts`'s existing `completenessCountForWarehouse`/`idCollisionMessageForWarehouse` helpers, the same data the inline per-row chip already computes, just surfaced more prominently right after the save that makes it accurate.

Destination naming, corrected: verified only two variants exist, not three. p-median-us and two-echelon both use `{id: "distances", label: "Distances"}` (same label, confirmed at `Workspace.tsx`'s two `inputEntriesForModel()` cases); only transport-coal differs, `{id: "laneCosts", label: "Lane costs"}`. The toast picks its label from `inputEntriesForModel(modelId)` directly rather than hardcoding "Distances" — no third "Leg distances" label exists in the actual UI.

## Risks and gaps

**External dependency (Nominatim)**
- No API key, no SLA — the script depends on a free public service that can throttle, block, or go down mid-run. Fixed: the script is resumable (Section 2), so a mid-run throttle doesn't force starting over.
- Reverse-geocoded postcodes are approximate (nearest addressable point to a lat/lng centroid), not authoritative — acceptable since `zip` is display-only and never reaches the solver, but the values shown to students won't always be the "textbook-correct" zip for a given city.
- OSM coverage is sparser outside dense urban areas. US locations (well-mapped) should resolve reliably; two-echelon's Australian refineries/mines are more remote and may return no postcode for some rows — the "Australian postcodes" ask may end up partially, not fully, satisfied. The script logs misses rather than failing, so this surfaces as a known gap in the completion report, not a silent one.

**Breaking API changes**
- Removing `POST /scenarios/compare` and `POST /scenarios/:id/reset-to-baseline` is real, irreversible API-surface removal (per explicit confirmation) — any consumer outside this frontend (a grader script, a saved Postman collection, direct curl use) breaks silently with no deprecation window.
- Removing `CompareRejection` and any other compare-specific OpenAPI schemas needs a check that nothing else references them before deletion — a missed reference would surface as a codegen/typecheck failure, which the gate catches, but it's worth being deliberate about during implementation rather than relying on the gate alone to notice.

**Product-capability regression**
- Scenario comparison (Compare Scenarios in Reports, and the standalone `Compare.tsx` page) goes away entirely with no replacement. If comparing two solved scenarios side-by-side turns out to matter later, it has to be rebuilt from scratch — this phase doesn't preserve the diff logic (`compareDiff.ts`) behind a smaller surface, it removes the feature.
- Reset-to-Baseline going away means there's no longer a one-click way to undo accumulated overrides on a scenario — the only path back is deleting overrides manually, one at a time, through the Warehouses/Customers tables.

**New feature complexity (Input Map + click-to-place)**
- A new Leaflet map component per model is real, non-trivial surface — click-event handling can conflict with existing marker click handlers. **Fixed:** Section 3's draft-marker + Confirm/Cancel step (a click no longer immediately commits anything — the location is visually verifiable and cancelable before the add-form even opens).
- Clicking outside the model's meaningful area (ocean, another country, wildly off the existing bounds) isn't explicitly guarded against beyond whatever `mapBounds.ts`'s existing `maxBounds` already restricts. **Not fixed** — the draft-marker Confirm step gives a human a chance to notice and Cancel, but there's no automated bounds/sanity check on the click itself; still a real gap if a student clicks carelessly and confirms anyway. Left as a follow-up, not blocking.
- Which entity type a click adds. **Fixed:** Section 3's placement-kind toggle + `kind` parameter on `onPlacePoint`.
- Click-to-place fills lat/lng but does not itself solve the existing "missing distances to every customer" requirement for a newly added facility, and the original design's toast couldn't have shown an accurate count at Confirm-time anyway (precheck data is keyed to the last *saved* state). **Fixed:** Section 3's two-step Confirm-then-Save-then-report flow, with per-model destination naming corrected (Distances / Lane costs, not a third invented "Leg distances" label). The underlying manual-distance-entry requirement itself remains unchanged and out of scope — only its visibility is fixed.

**Known pre-existing gaps this phase sits on top of, unresolved**
- Two-echelon's added-customer id-collision check is still asymmetric with its added-refinery check (a Minor follow-up noted at the end of the original SCN v0.3 branch review) — not addressed here.
- Brazil's missing dataset-browsing UI (explicitly out of scope, confirmed) means Brazil's gap relative to the other 3 models widens further after this phase — it now also lacks Input Map and the new table columns, on top of already lacking Warehouses/Customers tables.

**Process/scope risk**
- This is the largest single phase this session — five real subsystems (data sourcing, a new map feature, table changes, multi-layer removal, renames) bundled under one spec, with real file contention between tracks. **Fixed:** see "Sequencing for agent-team execution" below. Two genuine collisions were found by checking every track's file list against every other track's, not just the one pair (A/D on `Workspace.tsx`) originally caught — a second, equally real one exists between Track A and the zip schema/codegen work (both touch `openapi.yaml` and the same generated-client output). A third suspected collision (Track C and Track D both needing "the four entity-tab files") was checked directly against the code and **did not hold up** — Section 1's column work lives entirely in `components/tables/{Warehouse,Customer,Mine,Station}Table.tsx`, while Section 3's add-form prefill work lives in `components/workspace/tabs/{Warehouses,Customers,Mines,Stations}Tab.tsx` — confirmed disjoint by reading `Workspace.tsx:1051-1052`'s `dataset.warehouses` passthrough (no reshaping in between). C and D stay parallel with each other; both are now sequenced after Track A instead, for their own independent reasons (openapi.yaml and Workspace.tsx respectively).

## Sequencing for agent-team execution

Not five independent run-and-forget tracks — real file contention exists between some of them, found by checking each track's actual file list against every other track's, not assumed. Structured as three waves with an explicit, gate-verified checkpoint between each.

**Wave 1 (parallel):**
- **Track A (removals + renames)** — touches `openapi.yaml` (removing the compare/reset-to-baseline endpoints) and `Workspace.tsx`/`SidebarTree.tsx`. No dependency on anything else in this phase.
- **Track B (postal-code script only)** — the reverse-geocode script and its writes to the base dataset JSON files (`solvers/*/dataset/*.json`) plus each affected package's `version.json`. Deliberately scoped to *only* this — it does not touch `openapi.yaml`, `lib/dataset-schema`, or any generated code, so it's genuinely safe to run parallel with Track A (unlike the schema/codegen zip-plumbing work, which isn't part of this track — see Track C below).

**Checkpoint 1** — both merge to the phase branch; re-run the full gate (typecheck + api-server + studio + solver pytest, including `test_datasets.py` for Track B's `version.json` updates) on the *combined* state, not each track's state independently.

**Wave 2 (parallel, both sequenced to start from post-Checkpoint-1 `main`):**
- **Track C (table columns + zip plumbing)** — the three-layer zip fix from Section 2 (`lib/dataset-schema` Zod schemas, `transportCoalDataset.ts`/`twoEchelonDataset.ts` field-list updates, `openapi.yaml`'s `WarehouseCandidate`/`Customer` + codegen) plus the actual column rendering in `WarehouseTable.tsx`/`CustomerTable.tsx`/`MineTable.tsx`/`StationTable.tsx`. Bundled into one track because the column work is meaningless without the plumbing that makes `zip` real data. Built on post-Checkpoint-1 `main` specifically because it edits `openapi.yaml` — the same file Track A already edited to remove two endpoints; sequencing after A avoids that collision the same way Track D avoids its own.
- **Track D (Input Map + click-to-place)** — touches `Workspace.tsx` (`inputEntriesForModel()`, tab rendering, `SidebarTree` wiring) plus new files (`InputMapTab.tsx`) and the four `*Tab.tsx` wrapper components' add-form callbacks. Built on post-Checkpoint-1 `main` because it touches `Workspace.tsx`, the same file Track A already modified. **Confirmed independent of Track C**: C's files (`components/tables/*.tsx`) and D's files (`components/workspace/tabs/*.tsx`, `Workspace.tsx`) are disjoint — verified directly against the code, not assumed.

**Checkpoint 2** — both merge, full gate re-verified on the combined state again. This is a real barrier, not just "runs after": Track E's tests need C and D present *together* to write meaningful joint coverage (e.g. a Playwright spec that adds a warehouse via Input Map click-to-place, confirms it, and asserts the new row appears correctly in the Warehouses table) — split per the correction below, since a map-added row and a base-dataset row don't have the same postal-code guarantee.

**Wave 3:**
- **Track E (test coverage)** — dispatched only once Checkpoint 2 passes. Its acceptance coverage is split, not one blended assertion: (a) a **base-dataset row** test verifies City/State/Lat/Lng/Zip all render correctly (zip is real, sourced by Track B/C); (b) a **map-added row** test (via Input Map click-to-place → Confirm → add-form submit) verifies City/State/Lat/Lng render with the clicked coordinates, and explicitly asserts no Zip value is claimed for it — consistent with Section 1's rule that postal codes are base-dataset-only, since the one-time reverse-geocode script never runs against runtime-added rows.

**Manual QA** — after Track E merges, controller-run, not a subagent task (matches every prior phase).

## What this deliberately does not cover

- Brazil's missing dataset-browsing UI (explicit decision: out of scope, pre-existing boundary).
- Any change to `solve.py`/the solver's actual optimization logic — `zip` is display-only, never a solver input.
- Deleting `useCompareScenarios`'s underlying comparison *concept* from `compareDiff.ts` if anything else still imports it (checked during implementation; if genuinely unused after Reports+Compare.tsx removal, it goes too — if something else still depends on it, it stays and gets noted).
- An automated bounds/sanity check on Input Map clicks beyond the existing `maxBounds` restriction (see Risks — left as a human-in-the-loop check via the Confirm step, not a hard validation rule).
