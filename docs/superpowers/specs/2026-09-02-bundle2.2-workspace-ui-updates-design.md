## Global Constraints

- **DD-1:** base dataset files under `solvers/*/dataset/*.json` are never mutated. Reference distances read from the loaded dataset; overrides live only in scenario `inputs`.
- **No modelId hardcoding for capability gates** (repo's most-documented recurring bug class). Use manifest `capabilities` / scenario config, never `modelId === "..."` for per-model behavior.
- **Never edit generated code** (`lib/api-zod/src/generated/`, `lib/api-client-react/src/generated/`). Contract change = edit `openapi.yaml`, re-run Orval, commit spec + regen together.
- Ownership/anti-enumeration unchanged (404 never 403). Solver contract untouched — `e2e_accuracy.py` must stay green if any dataset/Python touched (it isn't expected to be here).
- Distance unit is model-driven (`manifest.distanceUnit`), already resolved via `useListModels()`; new distance UI reuses that, no hardcoded "mi".

## The 15 Updates

### Group A — Maps

**A1 (item 2/3) — Input Map layer toggles → checkboxes + legend follows toggles. Applies to ALL FOUR input maps.**
Replace `ToggleChip` buttons for the **layer** toggles with shadcn `Checkbox` rows, visually matching `OutputMapTab`'s toggle group, across all three live toolbars in `InputMapTab.tsx`. Applicability matrix:

| Model | Layer checkboxes | Show-inactive checkbox |
|---|---|---|
| p-median-us | Warehouses, Customers | yes (facility status) |
| p-median-brazil | Warehouses, Customers | yes (facility status) |
| transport-coal | Mines, Stations | **no** (no facility status) |
| two-echelon-gold-au | Refineries, Customers (mine implicit under Refineries layer) | yes (facility status) |

The place-pin controls (place-*) stay action buttons — one-shot placement, not layer toggles. `MapLegend` receives the per-model layer state and hides swatch groups for toggled-off layers (customers/stations off → hide demand bubbles + customer status swatches; warehouses/mines/refineries off → hide facility status swatches). Show-inactive checkbox is rendered only where facility status exists (not transport).

**A2 (item 4) — "Size customers by demand" toggle, Input Maps only, default ON, for every demand-bearing role.**
New `Checkbox` in each input-map toolbar. State `sizeByDemand`, default `true`. Covers every demand-bearing marker role: p-median customers, two-echelon customers, **transport stations** (stations carry demand). When ON: current quintile radius behavior (`EntityMarkers`/`makeQuintileRadius`). When OFF: every such marker renders at a **fixed radius of `FIXED_CUSTOMER_RADIUS = 6` px** (single locked constant, not implementer's choice). Output Map is out of scope for this toggle (keeps its current `scaleDemand`). Legend's demand-bubble section renders only when `sizeByDemand` is ON and the demand-bearing layer is on.

**A3 (item 10) — Customer Active/Excluded status in input-map dialogs, wired end-to-end for p-median-us + two-echelon.**
Two-state status (Active / Excluded — customers have no "forced open") added to **both** `EditCustomerDialog` and `CreateEntityDialog`'s customer branch.
- **Base customers** (all models that have them): persist to `customerOverrides[].status` (add `status: "active" | "excluded"` to the customerOverrides item schema in `openapi.yaml` + per-model Zod validators if absent; regen). Excluded base customers are already dropped from the p-median/two-echelon solve.
- **Added customers** (p-median-us + two-echelon only): add a new **`addedCustomers[].status: "active" | "excluded"`** field (default `active`). Thread it end-to-end: (1) manifest `inputsSchema` + Zod validators (p-median + two-echelon), (2) frontend `addedCustomers` input type + `EditCustomerDialog`/`CreateEntityDialog`, (3) effective-map projection (stop hardcoding added customers to `excluded: false`), (4) p-median + two-echelon **prechecks** (an excluded added customer no longer counts as active), (5) the merge/solver **payload boundary** (`excludedCustomerIds` already accepts added ids for these two models — populate it from `addedCustomers[].status === "excluded"` too), (6) tests. Solver `solve.py` itself is unchanged (it already honors `excludedCustomerIds`).
- **Role gate:** `CreateEntityDialog`'s generic `kind === "cs"` branch also serves **transport-coal stations** — the status control must be gated so stations never receive Active/Excluded (gate on the customer role config, not `kind` alone).
- **Brazil:** omitted from A3's added/excluded wiring — its solver applies no customer exclusion and it has no real input-map browsing path. Base-customer status control still renders where reachable but is out of A3's solver-correctness scope for Brazil.
- Excluded customers render with the existing inactive/excluded visual treatment on the input map.

**A4 (item 12) — Route hover box on the Output Map (model-unit-aware).**
Add a react-leaflet `<Tooltip>` (translucent, `pointer-events-none`) to each route polyline in `NetworkMap.tsx:442-479`. Content: `{fromCity} → {toCity}` and the leg length as **`{edge.distance} {distanceUnit}`** — `distanceUnit` threaded from `OutputMapTab` into `NetworkMap` (resolved via `useListModels()`, same as the metric overlay), never a hardcoded "mi". Cities resolved from the edge's `fromId`/`toId` against the effective dataset (same lookup the popup/markers use). RTL test must include a non-`mi` unit case so the capability is enforced, not accidental. No change to click-based `CustomerPopup`.

### Group B — Output tabs (p-median-us, capability/config-gated)

**B1 (item 5) — Hide Utilization when `capacityMode === "none"`.**
`OpenWarehousesTab` drops the Utilization column (header `56-58` + cell `66`) when the **snapshot** `capacityMode === "none"`. **Snapshot invariant:** read `capacityMode` from `displayedInputs` (the inputs that produced `displayedResult`), NOT `localInputs` or a current draft — an unsaved capacity-mode edit must not hide/show a column on an older solution. Config-driven, applies to any p-median model whose displayed solution has no capacity; two-echelon and capacitated scenarios keep the column. Not a modelId check.

**B2 (item 6) — Flows tab gated out of the sidebar for models without it.**
Gate the sidebar **output entries** by the active model's manifest `capabilities.outputGrids`. p-median-us `outputGrids` = `[openWarehouses, assignments, costSummary, serviceStats]` (no `flows`) → the Flows sidebar entry no longer renders. Closes the known C6.1 follow-up (sidebar previously showed all 5 regardless). The content-level gate at `2122-2148` stays as defense-in-depth. Models with `flows` in `outputGrids` (transport-coal, two-echelon) still show it.

**B3 (item 7) — Distances tab read-only reference table (new backend endpoint, p-median-us only).**
The frontend has no base distance matrix today (`GET /dataset` exposes only warehouses+customers). Add a **new read-only, ownership-scoped endpoint**:

`GET /scenarios/:id/reference-distances` → `{ pairs: [{ fromId, fromCode, toId, toCode, distance }], distanceUnit }`

- **Contract:** new operation in `openapi.yaml` + regen. Ownership-filtered (404 for non-owned, never 403). Scenario-scoped so it reflects the scenario's warehouse statuses.
- **Population:** base-entity × base-entity pairs from the loaded dataset's distance matrix, filtered to **active (potential + fixed-open, non-inactive) warehouses × base customers**. Excluded customers omitted. Added warehouses/customers are **not** in the base matrix — they carry no base row, so they are omitted from this reference table (their pairwise values live in the scenario's editable `distanceOverrides`, shown in the separate override grid below).
- **Model applicability:** **p-median-us only** for this bundle. Two-echelon's two-leg reference view is explicitly deferred (endpoint returns 422/empty or the tab hides the reference section for non-supported models — the tab reads a capability, not a modelId).
- **Frontend:** `DistancesTab` fetches this via a generated React Query hook and renders a scrollable, **virtualized** read-only table (up to ~26 active WH × 200 customers ≈ 5200 rows) labelled "Base distances (reference)", above the unchanged editable `distanceOverrides` add-row grid. Display-only — reads base data, writes nothing (DD-1 preserved).

**B4 (item 8) — Solution Summary moved after Output Map.**
Reorder `OUTPUT_ENTRIES` so `cost-summary` (Solution Summary) sits immediately after `Output Map`: Output Map, Solution Summary, Open Warehouses, Customer Assignments, [Flows], Service Stats.

**B5 (item 9) — Open-facility set per scenario in Solution Summary compare.**
In `CostSummaryTab` **compare mode**, add a row immediately after "Weighted avg. distance" listing each selected scenario's set of open facilities **by city name**. Correctness requirements from review:
- **Derivation:** reuse the established `openFacilityIds()` helper (which skips the two-echelon fixed-mine `mine_to_refinery` leg) — do NOT derive from raw unique `edges[].fromId`, which would list the mine as an open refinery.
- **Capability gate:** render only when the model has a facility-location choice. Gate on `capabilities.supportsFacilityStatus` (true for p-median-us/brazil/two-echelon, false for transport-coal) — NOT `supportsP` (excludes two-echelon, which B5 must include). The row does not render for transport-coal.
- **City lookup is scenario-specific:** a base facility id resolves through the loaded dataset, but an `aw-…` facility exists only in that compare column's own persisted `inputs.addedWarehouses`/`inputs.addedRefineries`. Resolve each column's open ids against **(base dataset ∪ that column's own persisted inputs)**, then apply the leg filter above.
- Uses each selected scenario's **latest persisted `inputs` alongside its latest persisted `result`** (compare already loads persisted scenarios). Single-scenario mode unchanged.

**B6 (item 11) — Display ID (not uid) for user-created warehouses.**
`OpenWarehousesTab` (`64`) and `AssignmentsTab` (`47-48`) map `fromId` (and `toId` where a warehouse) through a `displayCodeById` lookup (same pattern `DistancesTab` already uses) so user-created warehouses show their human ID, not the opaque `aw-…` uid. **Snapshot invariant:** build `displayCodeById` from `displayedInputs` (the inputs that produced `displayedResult`), NOT `localInputs` — a draft rename/move must not relabel ids on an already-displayed solution. Base-dataset entities are unaffected (their id === display code).

### Group C — App chrome

**C1 (item 1) — Global footer.**
Bottom-center footer on **every page that exists in the current router** (Landing, Login, Register, Workspace, Studio) — **Compare is removed from the router (Phase 3.2) and is NOT included**. Content: copyright symbol `©` followed by `Developed by hx1`.

Layout contract (review finding): both `Workspace` and `AppShell` own an `h-screen`/overflow-hidden viewport, so a naive sibling footer would sit below the viewport and a fixed footer would overlap the Workspace map. Use one shared **page-frame** strategy: a slim fixed bottom-center bar of locked height `FOOTER_H = 24px`, with each shell reserving that height (viewport becomes `calc(100vh - FOOTER_H)` / `pb-6` on the scroll container) so nothing overlaps map content. For Workspace, the footer must sit **inside the `.scn-theme` scope** so it inherits theme fonts/colors; non-themed pages use default styling. Acceptance coverage includes a narrow-screen case asserting no map/footer overlap.

**C2 (item 13/14/15) — Workspace header rework.**
Restructure the header into a **responsive three-zone grid** (`grid-cols-[auto_1fr_auto]`, not absolute-centering) so the centered summary cannot overlap the side clusters:
- **Left zone:** back-arrow + Scenario `<select>` (`select-scenario-context` testid preserved) moved here (from `2206-2223`).
- **Center zone (`1fr`, min-w-0):** chapter+summary block (`workspace-chapter-summary` testid preserved), now **untruncated / full text** — drop `max-w-[38%] truncate`, drop absolute positioning; it's the centered grid track, so its wrapped height contributes to header height and it's bounded by the side tracks (no overlap). Centered text within the track.
- **Right zone:** account cluster moved to the **top-right corner** — this shows the user's **email** (the auth contract exposes `id`/`email`/`role`, no display name; "user name" = email) + Logout. The result-history stepper + "Save as scenario" + Run-Optimizer cluster stay in their current relative position (to the left of Run Optimizer) — do not reposition them; they live in the right region as today.
- **Removed:** title/subtitle block (`2202-2205`); its `text-app-name` testid goes away with it (acceptable).

### Review Comments — 2026-09-02 (verbatim)

**Review status:** Needs revision before implementation planning. P1 findings below are blockers; P2 findings should be resolved in the same revision so the plan has unambiguous acceptance criteria.
