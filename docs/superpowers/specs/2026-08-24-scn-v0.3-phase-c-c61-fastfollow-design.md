# SCN v0.3 Phase C, Task C6.1 — Outputs & Reporting Fast-Follow Design

**Status:** Approved · **Date:** 2026-08-24 · **Scope:** fast-follow Phase C's p-median-us pilot (Open Warehouses/Customer Assignments/Cost Summary/Service Stats/Reports) to the other three models — `transport-coal`, `two-echelon-gold-au`, `p-median-brazil` — plus the new "Flows" grid the pilot deliberately left out (genuinely N/A for p-median-us).

## Relationship to the source plan

Source plan (`docs/superpowers/plans/2026-08-20-scn-v0.3-workspace.md` §4, row C6.1): "Fast-follow the three models (output grids vary by envelope shape; Reports identical)." This doc resolves the one thing that row leaves unspecified: which grid applies to which model, and how the gating is implemented so it doesn't repeat this repo's most-documented recurring bug class.

## Real finding that changes this fast-follow's shape vs. Phase B's

Phase B's Brazil carve-out (B6.3) was forced because Brazil's *input* override tables (Warehouses/Customers/Distances) need to enumerate the **full base dataset** to show alongside overrides, and `GET /dataset` has no `p-median-brazil` entry — a real, still-open backend gap.

Phase C's four output tabs (`AssignmentsTab`/`OpenWarehousesTab`/`CostSummaryTab`/`ServiceStatsTab`) take only `{result: SolveResult | null, scenarioId: number}` as props — confirmed directly against their real current signatures. They derive everything from the scenario's own already-solved `result`, never from a separate dataset query. **Brazil's missing dataset endpoint does not block its output tabs.** This fast-follow gives Brazil full output-tab parity with p-median-us, closing a real capability gap rather than repeating Brazil's input-side carve-out.

## Backend design

- **New `flows` export entity**: `FlowTemplateRow = {templateVersion, fromId, toId, flow, distance, band}` — structurally near-identical to `AssignmentTemplateRow` (rename `customerId`→`toId`/`warehouseId`→`fromId` since transport-coal's edges aren't customer/warehouse-typed), built via `buildFlowRows(result)`/`flowRowsToCsv(rows)` in `templates.ts`, following the exact same pattern as the four existing row-builder pairs.
- **Export route generalization**: replace the current hardcoded `if (scenario.modelId !== "p-median-us")` 422 (in the `OUTPUT_ENTITIES` branch) with a per-model-per-entity check driven by each model's manifest `capabilities.outputGrids` list (see below) — one list to keep in sync per model, not a growing if/else chain.
- **No solve.py/merge_inputs.py changes.** Every grid derives from the already-standardized `ResultEnvelope` (G2.1, Phase 3.5) — this fast-follow is a pure read-side extension.

## Frontend design — capability-driven gating, not another per-model if/else

This repo has hit the same bug class **five-plus times** (documented repeatedly in `CLAUDE.md`'s Gotchas and Chapter 10's post-launch rounds): a shared component's per-model gate gets updated for the model that prompted the change, and silently not updated for a sibling model that needed the same update. `model-integration-precheck.md`'s Gate 1 checklist exists specifically to catch this at review time — but review-time catching means it already shipped broken once.

Instead of extending the existing hardcoded gates in `Workspace.tsx`'s `renderTabContent()` (`if (modelId !== "p-median-us") return placeholder`) to a 4-way if/else, add a manifest-driven capability list:

```json
// solvers/<model-id>/manifest.json, new field under "capabilities"
"capabilities": {
  "supportsP": true,
  "capacityModes": ["none", "uniform", "per_wh"],
  "demandEditable": true,
  "outputGrids": ["openWarehouses", "assignments", "costSummary", "serviceStats"]
}
```

- p-median-us / p-median-brazil: `["openWarehouses", "assignments", "costSummary", "serviceStats"]`
- transport-coal: `["flows", "costSummary", "serviceStats"]`
- two-echelon-gold-au: `["openWarehouses", "flows", "assignments", "costSummary", "serviceStats"]`

`Workspace.tsx`'s `OUTPUT_ENTRIES` sidebar list and `renderTabContent()`'s output-grid branch both read this list (via the already-fetched `activeModelManifest` — `Workspace.tsx` already queries `useListModels()` for `countryBounds`, so `capabilities.outputGrids` rides along for free) instead of each hardcoding a per-model string. Adding a 5th model in the future means editing one manifest field, not hunting every gate across the codebase — this directly closes the bug class the fast-follow's own review process would otherwise just re-catch.

**New `FlowsTab.tsx`**: same read-only grid pattern as the four existing tabs (table + Download CSV button), columns `From / To / Distance / Flow`, filtering `result.edges` to whichever leg(s) apply generically (transport-coal has one edge type, uses all edges; two-echelon filters to `leg === "mine_to_refinery"`).

**`ReportsTab`/compare fold-in**: no changes. Confirmed model-agnostic already (`pickBaseline`, `diffInputs`/`diffOutputs`, the cumulative-band-rollup helper — none reference a model id).

## What this design deliberately does not cover

- Any change to `solve.py`, `merge_inputs.py`, or the result envelope's shape.
- Retrofitting the *input*-side per-model gates (`inputEntriesForModel`, `WarehousesTab`/`CustomersTab`'s capability gates) to the same manifest-driven pattern — out of scope for this fast-follow; worth a separate follow-up if the team wants to close that bug class everywhere at once, not bundled into an outputs-only task.
- The C4.2 clipboard-copy implementation — separate, already-spiked, already-deferred piece of work.
