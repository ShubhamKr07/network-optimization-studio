- **The studio vitest suite flakes under load from ANOTHER SESSION'S test run, and the failures name files your branch never touched.** Observed 2026-09-29 on `ch5-delivery`: two consecutive full `pnpm --filter studio test` runs reported 14 and then 36 failures across `DistancesTab`, `JadeDistancesTab`, `JadeFlowsTab`, `Studio`, `Workspace`, `CustomerTable` and `ImportDialog`, every one shaped `Test timed out in 5000ms`. Root cause, traced live via `ps aux`: a **different Claude Code session, in a different worktree on the same machine** (`/Users/shubhamkr/nos-ch4ux-6`), was running its own `pnpm --filter studio test` concurrently. A third run with zero concurrent vitest processes was clean at 2168/2168. Seen again 2026-10-05 on `agents-opus-ponytail` with **no** concurrent session: 3 files / 9 tests red, then 126/126 and 2310/2310 clean on an immediate re-run — so a `pnpm --filter studio test` that follows a long api-server run in the same session is load-sensitive on its own, not only against another worktree. (The failing file names were not captured that run; don't assume they were the seven named above.) This is the same contention class already documented for api-server and Playwright, but it had never been recorded for studio vitest — and it is more misleading here, because the failing files look like a broad regression in shared components rather than a flake. **Before trusting any full studio-suite result as a gate — especially the pre-merge gate — check for concurrent runs and require 0.** Parallel agent worktrees are now the normal way this repo runs, so assume contention rather than a regression when unrelated files time out together.

  Use `ps aux | grep "[v]itest" | grep -vc "zsh -c"`, **not** `ps aux | grep -c "[v]itest"`. The bare count also matches the agent's own `zsh -c` wrapper — whose command line contains the pattern text — so it reports 2 when the real answer is 0, and "require 0" becomes unsatisfiable. Confirm with `ps aux | grep "[v]itest" | grep -v "zsh -c"` and read the actual command lines before concluding anything; a count you cannot see the rows behind is the same class of non-discriminating check as everything else on this list.

  **Never chain that check with `&&` — `grep -c` exits 1 when the count is 0, so the success case is the one that short-circuits.** `grep -vc "zsh -c" && pnpm --filter api-server test` silently skips the suite precisely when the machine IS quiet, and prints the all-clear while doing it (hit 2026-10-09, CH4O-13). Assign it and test it: `cnt=$(… | wc -l | tr -d ' '); [ "$cnt" = "0" ] || exit 1`. Same family as the `git checkout main | tail -2 && git merge` incident in Branch discipline — a guard whose exit code is read from the wrong command is worse than no guard, because it reports success.
