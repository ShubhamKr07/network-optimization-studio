# Input Map v2 — Implementation Plan

> **For agentic workers:** This plan is executed via the **agent team** (role-based parallel dispatch: `backend-engineer` / `frontend-engineer` / `qa-sdet`), NOT sequential subagent-driven-development — per the standing repo preference. The controller dispatches each wave's file-disjoint tasks concurrently in isolated worktrees, cherry-picks each into an orchestration worktree, re-runs the full gate on the combined state, then merges. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Turn the p-median-us Input Map into a full map-first editing surface — status symbology, inspect, create/edit/move/copy/delete, auto-estimated distances — round-tripping to the input grids.

**Architecture:** Leaflet divIcon SVG markers over the existing `InputMapTab`; scenario-local edits write the existing `inputs` JSONB via the current manual-Save path; a backend normalization step auto-fills missing added-entity distances as `estimated` haversine on every persist path. Added entities carry a stable opaque `id` (join key) + a derived `displayCode`. Frontend owns the gazetteer + id/displayCode generation; the solver is untouched.

**Tech Stack:** React + Vite + react-leaflet + wouter + TanStack Query (frontend); Express 5 + Drizzle + Zod (backend); PuLP/CBC (solver — unchanged this phase).

**Spec:** `docs/superpowers/specs/2026-08-31-input-map-v2-design.md` (rev. 2 — read §2 decisions D1–D9, §6 backend, §7 frontend, §8 consistency).

## Global Constraints

- **DD-1: base dataset immutable.** No `solvers/*/dataset/*.json` write, ever. Base entities get only `warehouseOverrides`/`customerOverrides` (status/capacity/demand). No move/delete/id-change on base.
- **Pilot = p-median-us only.** All v2 behavior gates on `modelId === "p-median-us"`. The other three models keep today's behavior unchanged — never regress them. p-median-brazil's input-map tab stays its **current placeholder** (no `GET /dataset`), never the Task-4 map.
- **Stable identity (D7).** An added entity's `id` is an opaque uid and is the **join key** `distanceOverrides` reference — it **never changes** (backend/precheck/`merge_inputs.py` untouched). `displayCode` (`WH-STATE-CITY-SEQ`) is a display-only label, regenerated on move. Never re-key `distanceOverrides` on move; never touch the `warehouseOverrides`/`customerOverrides` arrays for an added entity.
- **Solver untouched.** No `solve.py`/`merge_inputs.py` change. `estimated`/`displayCode` are ignored by the solver. `e2e_accuracy.py` must pass **87/87 unmodified** (hard rule #2).
- **No OpenAPI/codegen change.** `inputs` is opaque `object` in the contract; these shapes live only in `pMedian.ts` (backend Zod) and frontend TS. Never edit `lib/api-zod`/`lib/api-client-react` generated files (hard rule #1).
- **Manual-Save-only** Workspace contract (SCN v0.3 standing decision): no auto-save/debounce. Map edits mutate `localInputs`; nothing persists until the user Saves.
- **Overlays not Leaflet Popups.** Details card / action menu / dialogs render in React over the map container, never as a `<Popup>` nested in a `<Marker>` (repo gotcha).
- **Estimation is one normalizer on every persist path (D8):** `fillEstimatedDistances` runs on `PATCH`, `POST` create, and `/import/apply` (p-median-us only), then the result is **revalidated** against the p-median schema.
- **One task = one commit**, message `[<task-id>] <summary>`, ending with the `Co-Authored-By` trailer.
- **Verification gate** (run on merged state before a wave closes): `pnpm run typecheck && pnpm --filter api-server test && pnpm --filter studio test` and, only if Python changed (it won't), the solver pytest + `e2e_accuracy.py`. Local api-server tests need `DATABASE_URL="postgresql://shubhamkr@localhost:5432/nos_dev"` inline.

```ts
import { WAREHOUSES, CUSTOMERS } from "../data/dataset.js";
import { buildActivePMedianIds } from "./precheck.js";
import { pMedianInputsSchema, type PMedianInputs } from "../validation/inputs/pMedian.js";

interface Coord { lat: number; lng: number; }
interface RoleDataset {
  warehouses: readonly { id: string; lat: number; lng: number }[];
  customers: readonly { id: string; lat: number; lng: number }[];
}
const DEFAULT: RoleDataset = { warehouses: WAREHOUSES, customers: CUSTOMERS };

const R_MI = 3959;
const MIN_DISTANCE_MI = 0.1;
const rad = (d: number) => (d * Math.PI) / 180;
export function haversineMiles(a: Coord, b: Coord): number {
  const dLat = rad(b.lat - a.lat), dLng = rad(b.lng - a.lng);
  const s = Math.sin(dLat / 2) ** 2 + Math.cos(rad(a.lat)) * Math.cos(rad(b.lat)) * Math.sin(dLng / 2) ** 2;
  return 2 * R_MI * Math.asin(Math.min(1, Math.sqrt(s)));
}

/** Canonical p-median normalization: fill missing ACTIVE added-involving
 *  distances as estimated haversine (clamped), then revalidate. Pure. */
export function fillEstimatedDistances(inputs: PMedianInputs, dataset: RoleDataset = DEFAULT): PMedianInputs {
  const added = inputs.addedWarehouses ?? [];
  const addedC = inputs.addedCustomers ?? [];

  // Role-scoped coordinate maps — never merged, so a same-string customer id
  // cannot overwrite a warehouse coordinate (ids are role-scoped, matching
  // precheck/solver).
  const whCoord = new Map<string, Coord>();
  for (const w of dataset.warehouses) whCoord.set(w.id, { lat: w.lat, lng: w.lng });
  for (const w of added) whCoord.set(w.id, { lat: w.lat, lng: w.lng });
  const custCoord = new Map<string, Coord>();
  for (const c of dataset.customers) custCoord.set(c.id, { lat: c.lat, lng: c.lng });
  for (const c of addedC) custCoord.set(c.id, { lat: c.lat, lng: c.lng });

  const addedWhIds = new Set(added.map(w => w.id));
  const addedCustIds = new Set(addedC.map(c => c.id));
  // buildActivePMedianIds takes a PrecheckDataset ({id}[] per role) — the
  // RoleDataset is structurally compatible (extra lat/lng ignored), no cast.
  const { activeWarehouseIds, activeCustomerIds } = buildActivePMedianIds(inputs, {
    warehouses: dataset.warehouses,
    customers: dataset.customers,
  });
  const activeAddedCustIds = activeCustomerIds.filter(id => addedCustIds.has(id));

  const overrides = [...(inputs.distanceOverrides ?? [])];
  const have = new Set(overrides.map(o => o.fromId + "|" + o.toId));

  for (const whId of activeWarehouseIds) {
    const required = addedWhIds.has(whId) ? activeCustomerIds : activeAddedCustIds;
    for (const custId of required) {
      const key = whId + "|" + custId;
      if (have.has(key)) continue;
      const a = whCoord.get(whId), b = custCoord.get(custId);
      if (!a || !b) continue; // no coords -> precheck still flags it
      const d = Math.max(MIN_DISTANCE_MI, Math.round(haversineMiles(a, b) * 10) / 10);
      overrides.push({ fromId: whId, toId: custId, distance: d, estimated: true });
      have.add(key);
    }
  }
  // Revalidate: the normalizer's output must satisfy the same schema.
  return pMedianInputsSchema.parse({ ...inputs, distanceOverrides: overrides });
}
```
