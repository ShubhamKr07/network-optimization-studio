# Input Map v2 — Implementation Plan

> **For agentic workers:** This plan is executed via the **agent team** (role-based parallel dispatch: `backend-engineer` / `frontend-engineer` / `qa-sdet`), NOT sequential subagent-driven-development — per the standing repo preference. The controller dispatches each wave's file-disjoint tasks concurrently in isolated worktrees, cherry-picks each into an orchestration worktree, re-runs the full gate on the combined state, then merges. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Turn the p-median-us Input Map into a full map-first editing surface — status symbology, inspect, create/edit/move/copy/delete, auto-estimated distances — round-tripping to the input grids.

**Architecture:** Leaflet divIcon SVG markers over the existing `InputMapTab`; scenario-local edits write the existing `inputs` JSONB via the current manual-Save path; a new backend service auto-fills missing added-entity distances as `estimated` haversine on Save. Frontend owns the gazetteer + ID generation; the solver is untouched.

**Tech Stack:** React + Vite + react-leaflet + wouter + TanStack Query (frontend); Express 5 + Drizzle + Zod (backend); PuLP/CBC (solver — unchanged this phase).

**Spec:** `docs/superpowers/specs/2026-08-31-input-map-v2-design.md` (read §2 decisions D1–D7, §6 backend, §7 frontend, §8 consistency).

## Global Constraints

- **DD-1: base dataset immutable.** No `solvers/*/dataset/*.json` write, ever. Base entities get only `warehouseOverrides`/`customerOverrides` (status/capacity/demand). No move/delete/id-change on base.
- **Pilot = p-median-us only.** All v2 behavior gates on `modelId === "p-median-us"`. The other three models keep today's Task-4 pin-only `InputMapTab` behavior unchanged — never regress them.
- **Solver untouched.** No `solve.py`/`merge_inputs.py` change. `estimated` is UI metadata the solver ignores. `e2e_accuracy.py` must pass **87/87 unmodified** (hard rule #2).
- **No OpenAPI/codegen change.** `inputs` is opaque `object` in the contract; `distanceOverrides` lives only in `pMedian.ts` (backend Zod) and frontend TS. Never edit `lib/api-zod`/`lib/api-client-react` generated files (hard rule #1).
- **Manual-Save-only** Workspace contract (SCN v0.3 standing decision): no auto-save/debounce. Map edits mutate `localInputs`; nothing persists until the user Saves.
- **Overlays not Leaflet Popups.** Details card / action menu / dialogs render in React over the map container, never as a `<Popup>` nested in a `<Marker>` (repo gotcha: stays closed until marker click).
- **One task = one commit**, message `[<task-id>] <summary>`, ending with the `Co-Authored-By` trailer.
- **Verification gate** (run on merged state before a wave closes): `pnpm run typecheck && pnpm --filter api-server test && pnpm --filter studio test` and, only if Python changed (it won't), the solver pytest + `e2e_accuracy.py`. Local api-server tests need `DATABASE_URL="postgresql://shubhamkr@localhost:5432/nos_dev"` inline.

```ts
import { WAREHOUSES, CUSTOMERS } from "../data/dataset.js";
import { buildActivePMedianIds } from "./precheck.js";
import type { PMedianInputs } from "../validation/inputs/pMedian.js";

interface Coord { id: string; lat: number; lng: number; }
interface CoordDataset { warehouses: readonly Coord[]; customers: readonly Coord[]; }
const DEFAULT: CoordDataset = { warehouses: WAREHOUSES, customers: CUSTOMERS };

const R_MI = 3959;
const rad = (d: number) => (d * Math.PI) / 180;
export function haversineMiles(a: { lat: number; lng: number }, b: { lat: number; lng: number }): number {
  const dLat = rad(b.lat - a.lat), dLng = rad(b.lng - a.lng);
  const s = Math.sin(dLat / 2) ** 2 + Math.cos(rad(a.lat)) * Math.cos(rad(b.lat)) * Math.sin(dLng / 2) ** 2;
  return 2 * R_MI * Math.asin(Math.min(1, Math.sqrt(s)));
}

/** Fill any missing ACTIVE added-involving distanceOverrides with estimated
 *  haversine. Never overwrites an existing row (manual or estimated). Pure. */
export function fillEstimatedDistances(inputs: PMedianInputs, dataset: CoordDataset = DEFAULT): PMedianInputs {
  const added = inputs.addedWarehouses ?? [];
  const addedC = inputs.addedCustomers ?? [];
  const coordById = new Map<string, Coord>();
  for (const w of dataset.warehouses) coordById.set(w.id, w);
  for (const c of dataset.customers) coordById.set(c.id, c);
  for (const w of added) coordById.set(w.id, { id: w.id, lat: w.lat, lng: w.lng });
  for (const c of addedC) coordById.set(c.id, { id: c.id, lat: c.lat, lng: c.lng });

  const addedWhIds = new Set(added.map(w => w.id));
  const addedCustIds = new Set(addedC.map(c => c.id));
  const { activeWarehouseIds, activeCustomerIds } = buildActivePMedianIds(inputs, dataset as never);
  const activeAddedCustIds = activeCustomerIds.filter(id => addedCustIds.has(id));

  const overrides = [...(inputs.distanceOverrides ?? [])];
  const have = new Set(overrides.map(o => o.fromId + "|" + o.toId));

  for (const whId of activeWarehouseIds) {
    const required = addedWhIds.has(whId) ? activeCustomerIds : activeAddedCustIds;
    for (const custId of required) {
      const key = whId + "|" + custId;
      if (have.has(key)) continue;
      const a = coordById.get(whId), b = coordById.get(custId);
      if (!a || !b) continue; // no coords -> can't estimate; precheck still flags
      overrides.push({ fromId: whId, toId: custId, distance: Math.round(haversineMiles(a, b) * 10) / 10, estimated: true });
      have.add(key);
    }
  }
  return { ...inputs, distanceOverrides: overrides };
}
```
Note: `buildActivePMedianIds`' `dataset` param is typed `PrecheckDataset` (`{id}[]`); the coord dataset is structurally compatible (has `id`) — the `as never` sidesteps the extra-fields mismatch. If a cleaner cast is available, prefer it.
