## 1. Design Decisions

**DD-1 — Immutable dataset + scenario deltas.** All network edits live inside `scenario.inputs` as three new families: `addedWarehouses[]`, `addedCustomers[]`, `distanceOverrides[{fromId,toId,distance}]`. Dataset files on disk are never written. Consequence: `computeInputsHash` automatically covers edits, so `result_cache` and staleness need **zero changes**.

**DD-2 — Long-format distances** (`from_id,to_id,distance`, one row per pair) for storage, import, export, and the grid. Rationale: reuses the row-per-entity import pipeline with `(from_id,to_id)` as composite key; schema-stable when entities are added (rows append, columns never change); sparse override files are naturally valid; generalizes to two-echelon's two leg types where a matrix cannot. **Corrected claim (review 2026-08-20):** the "matches `distances.json` shape, no pivots" argument holds for `transport-coal` (`"KY,LAX"` keys), `two-echelon-gold-au` (`"kalgoorlie,daggar-hills"`), and `p-median-brazil` (`"ANP,SP"` keys — confirmed ID-keyed, verified directly against the dataset). The **pilot model `p-median-us` is the sole outlier** — `distances.json` keys are `"1,2"` numeric index pairs, and `warehouses.json`/`customers.json` are index-keyed dicts with the real string ID (`ALN`, `ATL`) nested as a field. Overrides remain ID-keyed at the user/API boundary regardless (students think in IDs, not indices), so the merge helper owns an explicit id↔index bridge for `p-median-us` only — task B1.3. `p-median-brazil`'s B6.3 fast-follow is a straight port, no bridge work required. DD-1 forbids the alternative of rewriting `distances.json` to id-keyed format. A read-only matrix *display* toggle remains possible later; this decision covers formats only.

**DD-3 — Baseline by convention.** `pickBaseline(scenarios)`: the scenario named "Baseline" (case/whitespace-insensitive), else oldest by `createdAt`. One pure function, one call site (Reports). No `isBaseline` column, no uniqueness invariant, no migration, no set-baseline endpoint. Revisit only when a *server-side* consumer appears (e.g., instructor-locked baselines in the classroom phase — design the flag then, with its real consumer in view).

**DD-4 — Build Workspace alongside Studio, cut over per route.** New `pages/Workspace.tsx` + `components/workspace/*`; `chapters.ts` gains a per-chapter `workspace: boolean`; flipping a chapter is a one-line change. `Studio.tsx` is deleted only in Phase D after all four routes flip.

**DD-5 — Distance bands stay configurable**, defaulting to the wireframe's 250 / 500 / 750 cut points. Existing `bands.ts` machinery is kept; the wireframe's "fixed bands" note is treated as a default, not a constraint.

**DD-6 — Status vocabulary is display-only mapping.** UI labels Potential / Fixed-Open / Inactive ↔ stored enum `active / forced_open / inactive`. One mapping constant in the frontend; no API or schema change.

**DD-7 — "Save run as scenario" rides the result cache.** Creating a scenario from a solve-history entry = create scenario with that run's inputs snapshot, then trigger solve; `computeInputsHash` hits `result_cache`, so the "re-solve" returns instantly. Zero backend change.

**DD-8 — Additive-only inputs contract (rollback enabler).** Every new inputs field in this plan (`addedWarehouses`, `addedCustomers`, `distanceOverrides`) is optional-with-empty-default in Zod and in `manifest.json` `inputsSchema`, from the first deploy. Verified behavior of the current validators (default `.object()`, no `.strict()`): unknown keys are **stripped, not rejected** — so pre-B code never crashes on post-B scenario data. The consequence to manage: a rollback is a *silent semantic downgrade*, not a failure — old code solves those scenarios against the bare dataset, ignoring network edits, and (because stripped inputs hash differently) misses the cache and produces valid-looking but different results. §9 makes that downgrade explicit and controlled instead of silent. Note also that `SOLVER_CODE_HASH` (solve.py bytes salted into the cache key) already guarantees a solver revert can never serve results computed by the newer solver.

## 9. Rollback Strategy

**Standing guarantee:** this plan contains **zero DB schema migrations** — every persistent change lives inside already-jsonb columns. Therefore every rollback in this plan is *code + optional data-strip*, never a schema downgrade. This is the single strongest safety property of the whole plan; any future task that would break it must be escalated, not absorbed.

**Deployment mechanics (Render, three services per `render.yaml`):** rollback = redeploy the tagged commit per service. When a rollback crosses a contract change (only B1.2's `distances` entity enum), revert in consumer-first order — **studio → api-server** — so no live client ever sends an entity value the running API doesn't know.

### 9.1 Named rollback points

A rollback point (RP) is a git tag created **before** the first deploy of its phase, plus a pass/fail gate that must be green before the next phase may begin. Tags: `rp-a-pre-workspace`, `rp-b-pre-network-edits`, `rp-c-pre-reporting`, `rp-d-pre-decommission` (and per-model tags `rp-a-<model>` before each A5/B6/C6 fast-follow flip).

| RP | Rollback action | Blast radius | Data handling |
|---|---|---|---|
| **RP-A** | Flip the chapter's `workspace` flag back to Studio (one-line revert) — or redeploy `rp-a-pre-workspace`. Per-model tags make each fast-follow flip individually reversible. | One chapter route; Studio is byte-identical and its tests stayed green, so reverting restores exact prior behavior. | None — Phase A writes nothing new. |
| **RP-B** *(the solid one — see 9.2)* | Redeploy `rp-b-pre-network-edits` (studio → api-server), then run `strip-network-edits.ts`. | Scenarios containing network edits lose them and go **stale** (visible, honest state) instead of silently re-solving without them. All other scenarios untouched; cache self-heals via `SOLVER_CODE_HASH`. | Strip script is mandatory, idempotent, dry-run-first. Announce to users: "network edits were rolled back; affected scenarios are marked as changed." |
| **RP-C** | Redeploy `rp-c-pre-reporting`. | Reports/output tabs and clipboard feature disappear; `/compare` page still exists (not deleted until D) so comparison capability is retained during rollback. | None — Phase C reads existing result envelopes; writes nothing. |
| **RP-D** | `git revert` the deletion commit(s); redeploy. | Restores Studio + Compare + old e2e in one revert (D1.1 must therefore be a **single revertible commit**, not spread across PRs). | None. |

### 9.2 RP-B runbook (the designated "solid rollback point")

Phase B is the only phase where code and persisted data can disagree, so RP-B is the rollback point that must be *proven*, not assumed:

1. **Freeze:** flip the pilot chapter's `workspace` flag off if UI symptoms are the trigger (cheap first move — this alone reverts the whole user-facing surface while leaving B's backend, which is inert without UI to drive it).
2. **Revert code:** redeploy `rp-b-pre-network-edits` — studio first, then api-server.
3. **Reconcile data:** `strip-network-edits.ts --dry-run` → review count → run for real. Affected scenarios are now stale, which is exactly what a user should see: "your inputs changed" (they did — the rollback changed them), with re-solve one click away.
4. **Verify:** run the RP-B gate checks — Studio e2e suite green; a scenario that *had* edits solves clean against bare dataset and reports stale-then-solved; a scenario that never had edits still returns its **cached** result (proves the strip didn't touch it: unchanged inputs → unchanged hash → cache hit).
5. **Point of no return within B:** none — B is fully reversible at any moment, because the dataset files were never written (DD-1) and the schema never changed. The only true point of no return in the plan is **D1.1** (Studio deletion), which is why it is gated on all four models running Workspace in production for a soak period (suggest ≥2 weeks of real classroom use) with zero P1 issues.

### 9.3 Rollback drill (task BR-2)

Before Phase B's pilot deploy, execute the RP-B runbook once against a staging environment seeded with edited scenarios, and record the result in `docs/`. A rollback plan that has never been run is a hypothesis; this drill converts it into a procedure. (Precedent: the same discipline the import pipeline applies by re-validating at apply-time rather than trusting the preview.)
