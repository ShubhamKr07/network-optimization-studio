> **For agentic workers:** REQUIRED SUB-SKILL: This plan is executed via the **agent team** (`backend-engineer`/`frontend-engineer` roles per `AGENTS.md` and `.claude/agents/*.md`), dispatched in parallel waves — NOT `subagent-driven-development`'s one-task-at-a-time implementer+reviewer loop. Each task below is still its own commit with its own tests, and still gets a task-scoped review before being marked done; only the *dispatch* model changes (parallel role-based, not strictly sequential). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extend Phase C's four output grid tabs (Open Warehouses, Customer Assignments, Cost Summary, Service Stats) plus a new fifth tab (Flows) from p-median-us-only to all 4 models, gated by a new manifest-driven `capabilities.outputGrids` field instead of a hardcoded per-model check — closing this repo's most-documented recurring bug class (a shared component's per-model gate updated for one model, forgotten for a sibling) by construction rather than by review-time catching.

**Architecture:** A new `outputGrids: string[]` field on each model's `manifest.json` (validated by `lib/dataset-schema`'s `ManifestSchema`, exposed via `GET /api/models`'s OpenAPI contract) becomes the single source of truth both the backend export route and the frontend's tab-gating read — no model-id string comparisons anywhere in the gating logic. A new `flows` export entity + `FlowsTab.tsx` component fill the one genuinely new grid (mine→station for transport-coal, mine→refinery for two-echelon).

**Tech Stack:** Express 5 + Drizzle (backend, unchanged), React + Vite + Tailwind (frontend, unchanged), Zod (`lib/dataset-schema`), OpenAPI + Orval codegen, vitest/RTL + supertest for tests (unchanged).

## Global Constraints

- **Two independent validation layers currently gate `capabilities` and both silently strip unknown fields if not updated together** — this is the single most important fact in this plan, verified directly against real source, not assumed:
  1. `lib/dataset-schema/src/index.ts`'s `ManifestSchema` (backend Zod, used by `modelRegistry.ts` at server boot). Zod's default `z.object()` mode is "strip" — adding `outputGrids` to a manifest.json file WITHOUT adding it to this schema means `ManifestSchema.parse(raw)` silently drops it, no error, just data loss.
  2. `lib/api-spec/openapi.yaml`'s `ModelInfo.capabilities` schema — must be edited and Orval codegen re-run (`pnpm --filter @workspace/api-spec run codegen`, or the workspace-root `pnpm run typecheck:libs` step that follows it) or the frontend's generated `ModelInfoCapabilities` TS type simply won't have `outputGrids` on it (a compile error the moment frontend code tries to read it).
  Both must change in Task 1, in the same commit, or the feature silently doesn't work end-to-end.
- **`"flows"` already exists in `Workspace.tsx`'s `OUTPUT_ENTRIES` array** (added during Phase C, unused) but has no render branch and is excluded from the current output-grid gating `.includes([...])` array — it currently falls through to the generic placeholder, not the p-median-us-specific one. This plan intercepts it, not the generic fallback.
- **Grid-to-model mapping** (derived from each model's real `Edge`/`Edge.leg` shape, confirmed against `resultEnvelope.ts`, not guessed):

  | Model | `outputGrids` value |
  |---|---|
  | `p-median-us` | `["openWarehouses", "assignments", "costSummary", "serviceStats"]` |
  | `p-median-brazil` | `["openWarehouses", "assignments", "costSummary", "serviceStats"]` |
  | `transport-coal` | `["flows", "costSummary", "serviceStats"]` |
  | `two-echelon-gold-au` | `["openWarehouses", "flows", "assignments", "costSummary", "serviceStats"]` |

- **`buildFlowRows`'s filter**: `result.edges.filter(e => e.leg !== "refinery_to_customer")` — this correctly includes transport-coal's edges (which never carry `leg` at all, so the comparison is `undefined !== "refinery_to_customer"` → `true`, included) and two-echelon's `mine_to_refinery` edges, while excluding two-echelon's `refinery_to_customer` edges (which belong to Customer Assignments, not Flows). Verified against `buildOpenWarehouseRows`'s existing inverse pattern (`if (e.leg === "mine_to_refinery") continue`) at `templates.ts:711`.

```ts
export interface FlowTemplateRow {
  templateVersion: number;
  fromId: string;
  toId: string;
  distanceMi: number;
  band: number | null;
  flow: number;
}

// C6.1 — the transport-coal/two-echelon equivalent of Customer Assignments
// (genuinely N/A for p-median-us/brazil, which have no multi-leg or
// facility-less-LP shape). Filters out refinery_to_customer edges (those
// belong to Customer Assignments) — transport-coal's edges never carry
// `leg` at all, so they all pass this filter unfiltered; two-echelon's
// mine_to_refinery edges pass too. Mirrors buildOpenWarehouseRows'
// existing inverse leg-filter exactly (templates.ts, Phase C).
export function buildFlowRows(result: ResultEnvelope): FlowTemplateRow[] {
  return result.edges
    .filter(e => e.leg !== "refinery_to_customer")
    .map(e => ({
      templateVersion: TEMPLATE_VERSION,
      fromId: e.fromId,
      toId: e.toId,
      distanceMi: e.distance,
      band: e.band ?? null,
      flow: e.flow,
    }));
}

export function flowRowsToCsv(rows: FlowTemplateRow[]): string {
  const header = "template_version,from_id,to_id,distance_mi,band,flow";
  const lines = rows.map(r =>
    [r.templateVersion, r.fromId, r.toId, r.distanceMi, r.band ?? "", r.flow].join(","),
  );
  return [header, ...lines].join("\n") + "\n";
}
```

- [ ] **Step 3: Implement `FlowsTab.tsx`**

```tsx
import type { SolveResult } from "@workspace/api-client-react";
import { downloadEntityExport } from "@/lib/exportEntity";

interface FlowsTabProps {
  result: SolveResult | null;
  scenarioId: number;
}

// C6.1 — the transport-coal/two-echelon equivalent of Customer Assignments.
// Mirrors templates.ts's buildFlowRows filter exactly (exclude
// refinery_to_customer edges — those belong to AssignmentsTab) so the
// on-screen table and the CSV export never disagree.
function flowRows(result: SolveResult) {
  return result.edges.filter(e => e.leg !== "refinery_to_customer");
}

export function FlowsTab({ result, scenarioId }: FlowsTabProps) {
  if (!result) {
    return <div className="p-4 text-sm text-muted-foreground" data-testid="flows-empty">No solved result yet.</div>;
  }
  const rows = flowRows(result);

  return (
    <div className="flex flex-col h-full overflow-hidden">
      <div className="flex items-center justify-between p-2 border-b flex-shrink-0">
        <span className="text-sm font-medium">Flows</span>
        <button
          type="button"
          data-testid="button-download-flows-csv"
          className="text-xs border rounded px-2 py-1 hover:bg-muted"
          onClick={() => downloadEntityExport(scenarioId, "flows", "csv")}
        >
          Download CSV
        </button>
      </div>
      <div className="overflow-auto flex-1">
        <table className="w-full text-sm">
          <thead className="sticky top-0 bg-background border-b">
            <tr>
              <th className="text-left p-2">From</th>
              <th className="text-left p-2">To</th>
              <th className="text-right p-2">Distance (mi)</th>
              <th className="text-right p-2">Flow</th>
            </tr>
          </thead>
          <tbody>
            {rows.map(e => (
              <tr key={`${e.fromId}-${e.toId}`} data-testid={`flow-row-${e.fromId}-${e.toId}`} className="border-b">
                <td className="p-2">{e.fromId}</td>
                <td className="p-2">{e.toId}</td>
                <td className="p-2 text-right">{e.distance.toFixed(1)}</td>
                <td className="p-2 text-right">{e.flow.toLocaleString()}</td>
              </tr>
            ))}
          </tbody>
        </table>
      </div>
    </div>
  );
}
```
