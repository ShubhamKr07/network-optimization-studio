## Recommendations (prioritized)

### 1. Investigate the zero-export funnel end (high)
Exports are 0 for all four models, including 162 completed solves on `max-coverage-us`. The aggregates cannot say whether users don't want to export, can't find the export action, or whether the `exported` event isn't being captured. Check first that the export event is instrumented and firing (including the cost-summary and entity exports). If it is, review the discoverability of export after a solve completes.

### 2. Raise the stale-resolve rate (high)
`staleResolveRate` is 0.0377 (about 3.8%). The file gives no numerator or denominator, so we can't say how many scenarios that is. On its face, almost none of the stale scenarios are re-solved. Candidate actions:
- Make the stale badge more actionable, for example with an inline "Re-solve" button.
- Check whether users abandon stale scenarios or keep reading the old result.
- Add counts for stale-badge views and stale scenarios to the aggregates, so the rate can be read in context.

### 3. Fix event accounting for solves (medium)
Completed solves exceed triggered solves for two models: `max-coverage-us` (162 completed vs 156 triggered) and `two-echelon-jade-us` (59 vs 52). A completion without a matching trigger in the same week suggests one of these, though the data cannot tell which:
- Solves triggered in a prior week completed in this one.
- Some trigger paths (e.g. re-solves, async job recovery) don't emit `solveTriggered`.
- Completions are double-counted.

Resolve this before trusting solve-level funnel conversion figures.

### 4. Check that runtime and cache metrics are collected (medium)
`runtimeP50`, `runtimeP95` and `cacheHitRate` are all 0 despite 220+ completed solves. A p50 runtime of exactly 0 is implausible for a CBC solve, so this is more likely a metric that isn't populated than a real measurement. Don't draw performance conclusions from these fields until the pipeline is verified.

### 5. Solve failures and rejections: nothing to act on (info)
Both maps are empty, meaning none were recorded. That is consistent with healthy solves, but it also could mean failure events aren't captured. It is worth a one-time check that failure events fire, using a deliberately invalid scenario.

### 6. Low-volume models (low)
`p-median-us` (2 created) and `delivery-teaching-us` (1 created) are too small to support any funnel conclusion. Note that `delivery-teaching-us` shows 2 solves triggered from 1 created scenario, i.e. at least one re-solve of the same scenario. This may be normal iteration behaviour. Keep collecting data.

## Caveats
- One week of aggregates, with no prior-week baseline, so no trend can be stated.
- Per-model creation-to-solve ratios (e.g. about 2.7 solves per created `max-coverage-us` scenario) suggest iterative use, but solves in a week may belong to scenarios created earlier, so this is not a precise conversion rate.
