## Recommendations (prioritized)

### 1. Investigate the zero exports (highest priority)
No model recorded a single export, even though 28 solves completed. Either students don't find or don't value export, or the export event isn't being captured. First verify the export event fires, for example with a manual export in a test environment. If tracking is correct, look at how discoverable export is after a solve completes.

### 2. Fix or explain the funnel counts that don't line up
- `p-median-us` shows 7 solves completed against only 2 triggered.
- Every model except p-median-us has `solveCompleted` equal to `solveTriggered`.
- Completions can't exceed triggers within one funnel. This points to different event sources or time windows, for example solves of scenarios created in a prior week, or a missing or double-counted event.
- Until this is resolved, p-median-us trigger-to-complete conversion can't be read reliably. Audit the event definitions behind `solveTriggered` and `solveCompleted`.

### 3. Verify that runtime and cache metrics are instrumented
`runtimeP50`, `runtimeP95` and `cacheHitRate` are all 0 despite 28 completed solves. A real CBC solve is unlikely to take 0 ms. Most likely these fields are not populated in the aggregation. Confirm before using them for any performance decision. A cache hit rate of 0 may be real or may be the same gap.

### 4. Creation-to-solve funnel: usage is concentrated in few models
- `max-coverage-us` has 14 solves triggered and 0 scenarios created this week, so its usage is entirely on scenarios created earlier or elsewhere. It accounts for 14 of 23 triggers (about 61%).
- `p-median-us` has the most creations (5), but its funnel is the one with inconsistent counts (see item 2).
- `delivery-teaching-us` and `super-model` each had 1 creation and more triggers than creations, which suggests repeated solves per scenario.
- The data cannot show drop-off between creation and first solve for any model, because creation and solve counts are not cohort-linked. If that drop-off matters, add a per-scenario (not per-event) funnel.

### 5. Solve failures, rejections and staleness: no action
There were no failures, no rejections and a 0 stale-resolve rate. The data does not support any recommendation here. Note that a stale-resolve rate of 0 is ambiguous: it could mean no scenario went stale, or that stale scenarios weren't re-solved. The aggregates do not distinguish the two. Consider also recording how many scenarios were stale, so the rate has a visible denominator.
