# Drizzle schema (`lib/db/`) — gotchas

Moved out of the root `CLAUDE.md` so it loads only when working under this directory. The root file's Hard rules, Branch discipline, and cross-cutting Gotchas still apply. New gotchas scoped to this directory go here (hard rule #9).

- **Every timestamp column in this schema must be `timestamptz` (`{ withTimezone: true }`), because drizzle and Postgres disagree about what a naked `timestamp` means.** Drizzle writes *and reads* a naked `timestamp` as **UTC wall-clock**, but `defaultNow()`/`sql`now()`` store the **database session's local wall-clock** — so every DB-side-written value reads back wrong by the database's UTC offset, while every app-side `new Date()` write is correct. This is backwards from the intuitive guess, and the intuitive guess is dangerous: "just make all the writers `new Date()`" would break the stale-lease takeover at `jobRunner.ts:617` (`owner_heartbeat_at < now() - interval '60 seconds'`), which is correct today *only* because both sides are DB-side. It shipped as the solve overlay reading `Solving 25200s` — exactly 7h, this machine's `America/Los_Angeles` database offset — with 131 of 160 local `solve_jobs` rows carrying `finished_at - started_at` = exactly `25200`. Three traps worth keeping: (1) **a naked column is correct whenever the database happens to run in UTC**, which is the likely CI configuration, so a round-trip test can be green in CI while the bug is live in production — assert the column *type* too; (2) **probe through the ORM, not the driver** — the same experiment via raw `pg` gives a different skew (local-zone serialisation both ways) and supports the wrong conclusion; (3) **mixed writers in one column are a distinct bug from the offset** — `finished_at` had both forms, which made `max(finished_at)` (`landingSummary.ts`) a wrong value rather than a shifted one, and left historical rows permanently unattributable. Also note the fix *removes an accidental mask*: `isStale()` is a bare `inputsUpdatedAt > solvedAt` with no tolerance, and it only ever worked because this database's offset is **negative** — `inputs_updated_at` read back into the past, so it could never win the comparison. On a positive-offset database (`Asia/Kolkata`, +05:30) the identical code reads 19800s into the *future* and `isStale()` returns `true` for every solved scenario, permanently. The old behaviour was benign by luck, not by design, so both sides of that comparison must come from `now()`. Full account + migration SQL + rollback: `docs/ops/timestamptz-migration.md` — **and that runbook is not idempotent: running the conversion twice shifts every row by the offset again, silently, because `v AT TIME ZONE 'UTC'` on an already-`timestamptz` column re-interprets it in the session zone. Check the column types before running it.** **`sessions.expire` is the one deliberate exception**, because that table is dead (`auth.ts:4` marks it unused, zero writers, zero readers, 0 rows) — converting a table slated for removal buys nothing. Nothing depends on its type: `connect-pg-simple`/`express-session` are **not installed** (auth is a stateless signed cookie, `routes/auth.ts:77`).
