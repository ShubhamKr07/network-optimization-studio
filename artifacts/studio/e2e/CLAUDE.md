# Playwright e2e (`artifacts/studio/e2e/`) — gotchas

Moved out of the root `CLAUDE.md` so it loads only when working under this directory. The root file's Hard rules, Branch discipline, and cross-cutting Gotchas still apply. New gotchas scoped to this directory go here (hard rule #9).

- **`artifacts/studio/e2e/labs.spec.ts` is stale against local HEAD post-D0/D1.** It targets a remote Replit deployment by default (`E2E_BASE_URL`) and asserts on the pre-D0 API shape (`problemType`/`pValue`/`warehouseStatuses` as top-level scenario fields). Local HEAD now sends `{name, modelId, inputs}`. Left unfixed deliberately: updating the assertions now would only break the suite against the one target it can actually reach (the still-undeployed-with-D0 Replit instance). **The "no local dev proxy" half of this gap is resolved as of D5.2** — `vite.config.ts` has an opt-in dev proxy (`API_PROXY_TARGET` env var). To run e2e locally: start api-server (`DATABASE_URL=... PORT=3001 pnpm --filter api-server run dev`), then studio (`PORT=<any> BASE_PATH=/ API_PROXY_TARGET=http://localhost:3001 pnpm --filter studio run dev`), then `E2E_BASE_URL=http://localhost:<studio-port> npx playwright test` from `artifacts/studio`. **The studio dev server also needs `VITE_POSTHOG_KEY` and `VITE_SENTRY_DSN` set, or `posthog-analytics.spec.ts` and `sentry-capture.spec.ts` fail for a purely environmental reason and look like real breakage** — `analytics.ts:14` is a bare truthiness check, so nothing is ever captured and both specs assert against captures. DUMMY VALUES ARE CORRECT, not a workaround: both specs stub the ingest host before any request leaves the page (`posthog-analytics.spec.ts:63-65`, `sentry-capture.spec.ts:80-83`), and the DSN need only be syntactically valid. Use `VITE_POSTHOG_KEY=phc_local_dummy_key VITE_SENTRY_DSN=https://x@o.ingest.sentry.io/1`. (Added 2026-10-04: those two specs point AT this recipe, which could not run them, and a session following it reported two failures as environmental and called a gate clean while both specs had never executed.) `labs.spec.ts` itself still needs its assertions rewritten for the current API shape before it'll pass locally — `import.spec.ts` (D5.2) is the first spec written against current HEAD and passes.
- **`elementFromPoint` answers "what would a click hit", NOT "what is painted on top" — and for anything `pointer-events-none` those are opposite answers.** A deliberately click-through overlay correctly returns the element *underneath* it, so using it to prove paint order proves nothing and fails confusingly. Assert stacking with stacking: computed `z-index` plus `position != static` on the ancestor, and a bounding-box overlap. (Same call is perfectly sound when the click answer is the question — e.g. "does this canvas intercept clicks on the cards behind it?")
- **A form field's draft-until-commit pattern (commits only on blur/Enter, e.g. `useDistanceDraft`) means `.fill()` alone in a Playwright test can silently never reach a guarded write path at all** — the input visually shows the typed value but no `onChange`/write ever fires. Always follow a `.fill()` on such a field with an explicit blur or Enter, and verify the *effect* (a guard dialog appearing, a counter changing), not just the input's own displayed text.
- **Prefer committing a draft field via blur (click a neighboring field) over `.press("Enter")` when the commit is expected to open a dialog that steals focus.** Confirmed via trace replay: `.press("Enter")` on `ChenDistanceInput` reliably raced Radix's Dialog auto-focus and self-closed the just-opened freeze-confirm dialog within under a second, with zero console/network errors in between — a blur onto an already-stable different element sidesteps the race entirely and was 100% reliable across every re-run.
- **`readSolvedAt` is the standard e2e solve-completion signal — import it from `artifacts/studio/e2e/helpers/solvedAt.ts`, never re-declare it, and do NOT use it for a concurrent solve.** Capture the value *before* triggering and poll until it differs; polling for non-null is wrong because an already-solved scenario starts non-null. It beats the two obvious alternatives because the solve overlay is transient (a fast solve comes and goes between polls) and `output-map-tab` is a false positive when that tab was already open. **The hazard, currently unreachable but guaranteed to bite the first concurrent-solve spec:** `solvedAt` only advances when `jobRunner`'s publication CAS matches, and that `.where()` requires BOTH `latestSolveJobId = jobId` AND `solveInputRevision = enqueuedSolveInputRevision` (`jobRunner.ts:1481-1488`). A solve that *succeeds but is superseded* — a newer solve enqueued, or inputs edited, while it ran — deliberately does not publish, so `solvedAt` never changes and a `readSolvedAt` wait hangs for the full `SOLVE_TIMEOUT` and then fails **looking like a solver timeout**, which is the wrong diagnosis. **Safe today for a non-obvious reason — not because "specs are sequential".** `playwright.config.ts` sets `fullyParallel: false` but never sets `workers`, so Playwright defaults to ~half the cores and `fullyParallel: false` serialises only tests *within* a file; **spec files run in parallel**. The actual protection is that the CAS is per-scenario and every spec registers its own user and creates its own scenarios, so no two specs touch the same row — a future spec sharing or seeding a fixed scenario id would be exposed while still looking "sequential". CH4UX-6's in-flight lock narrows the UI path but is not an absolute: `src/pages/Workspace.tsx:3050-3059`'s own comment records that `enqueueSolve` has a second caller (`handleSaveAsScenario`) which does not re-run the guard, and closes with "Do not read this comment as 'the enqueue helper is single-entry' — it is not." That path creates *separate* scenarios, so it cannot cause same-scenario overlap. For a concurrent solve, wait on the specific job (`GET /api/scenarios/{scenarioId}/solve-jobs/{jobId}` — plural segment, `openapi.yaml:352` — which reports a terminal status whether or not its result was published). Extracted from seven byte-identical copies that had drifted to `id: string` in four and `id: number` in three; the shared helper takes `string | number` and casts the response instead of reading an implicit `any`, so a rename of the `solvedAt` field can no longer be silent in all seven.
- **A Playwright `.click()`/`.fill()` with no explicit `timeout` inherits the ENTIRE remaining test budget when the target never becomes actionable** (e.g. a `disabled` button, or an element that gets detached mid-actionability-check) — a 10-second problem silently becomes a multi-minute or full-timeout one, and the failure surfaces at some unrelated later line (often a `finally` block's cleanup call) rather than at the real stuck action. Bound any e2e interaction that follows a dialog opening, a disabled-state transition, or a history/step-navigation change with an explicit `{ timeout }`.
- **`pnpm e2e:gate` WITHOUT `E2E_BASE_URL` silently tests a REMOTE Replit deployment, not your local code.** `playwright.config.ts:3-5` defaults `BASE_URL` to a `https://…kirk.replit.dev` URL when the env var is unset, so the whole gate runs against a stale remote app: CH4O Task 12's first run produced **136 bogus failures** before this was caught. The trap was recorded for `labs.spec.ts` only (the entry above), but it governs **the entire gate**. Always run `E2E_BASE_URL=http://localhost:<studio-port> pnpm e2e:gate`. The consequence worth stating plainly: **any historical "e2e:gate green" claim in this repo was only ever about local code if `E2E_BASE_URL` was set** — an unqualified green from an earlier session is not evidence about local HEAD.
- **A spec that injects its own latency must budget the dependent assertion at SEVERAL MULTIPLES of the injected delay, not merely above it.** `chen-bands-units-qa.spec.ts:230` injected a 3s `**/api/models` route delay and budgeted the resolve-and-re-render at 6s — 2× looks like headroom and is none at all under 4 workers with real CBC solves in flight, and that was the mechanism behind its repeated gate failures (now 15s). This makes the failure **structural, not merely "load"**: the spec sets up its own race and loses it, so re-running it in isolation can hide a budget that is genuinely too tight. `chen-bands-units-qa.spec.ts` is the most load-sensitive file in the suite — Task 12 saw 2 of its ~9 tests destabilise, each with its own mechanism: the `"no distance ever renders under a guessed unit while the model manifest is still loading"` case (the 3s/6s budget above) and the `"unit-aware commit stores the correct canonical value…"` case, whose three no-auto-retry `inputValue()` reads now go through `toHaveValue` first. **Identify these by test NAME, not line number.** This entry first recorded the second one as `:395`; the fix commit on that same branch (`e4701d8`) shifted it to `:400`, so the line reference then pointed a reader at the band-editor test instead — the exact self-inflicted-correction loop the root file's flake entry warns about.
