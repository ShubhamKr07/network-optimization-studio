# API server (`artifacts/api-server/`) — gotchas

Moved out of the root `CLAUDE.md` so it loads only when working under this directory. The root file's Hard rules, Branch discipline, and cross-cutting Gotchas still apply. New gotchas scoped to this directory go here (hard rule #9).

- **Locking a shipped model silently deletes its test coverage — add a test-only unlock seam, and put the guard BEFORE the write.** `capabilities.locked` on a solver manifest (ch4-lock) withholds a chapter: the api-server 403s every scenario-scoped route for that model. Two traps, both hit for real. (1) The moment two shipped models were locked, **73 existing api-server tests stopped testing Chen/JADE behavior and started asserting 403** — the suites still passed conceptually but covered nothing. Fix: `setLockedModelsForTests(...)` in `middlewares/lockedModel.ts`, which those suites call to unlock for their own duration; it is a plain module-level variable, deliberately NOT an env var or config flag, so nothing in the running server can reach it. (2) A lock check placed after `db.update`/`db.delete` returns 403 **having already mutated the row** — two of the first placements did exactly that. `lockedModelGuards.test.ts` now reads the route source and fails both on a `:scenarioId` handler missing a check and on a check positioned after a write. Related: the lock is declared in two places by necessity (manifest for the server, `chapters.ts` for a synchronous Landing render with no live-card flash) and `lockedChapterDrift.test.ts` is what stops them drifting — it also asserts the comparison isn't vacuously empty, so deleting `locked` from both sides can't pass on two empty sets.
- **`import.meta.url`-relative paths lie once esbuild bundles them.** `artifacts/api-server`'s build (`build.mjs`, `bundle: true`) merges every source file into one `dist/index.mjs`; at runtime, `import.meta.url` for code that originated from *any* of those files resolves to that single output file's location, not its own true source path. A path computed via `path.dirname(fileURLToPath(import.meta.url))` that assumes the source layout (e.g. `src/data/`) works under vitest (unbundled) but silently breaks in the real built server. `pmedian.ts` already hardcodes around this for `solve.py`'s path; `data/dataset.ts` uses `findRepoRoot()` (walk up to `pnpm-workspace.yaml`) instead, which is correct in both contexts — prefer that pattern for anything new. Always verify against the actual built server (`pnpm --filter api-server run dev`), not just vitest, before trusting a new file-path computation.
- **An unwrapped drizzle call leaks its PARAMETER VALUES into every error sink, and `scrubEvent` does not stop it — wrap any query carrying user-authored text.** drizzle-orm 0.45.2 builds `DrizzleQueryError`'s message as `` `Failed query: ${query}\nparams: ${params}` `` and retains `this.params`, so a failing query puts the *values* into the thrown error's own message. `app.ts` then feeds that to three sinks: PostHog's `setupExpressErrorHandler`, `Sentry.setupExpressErrorHandler`, and `logger.error({ err }, …)`. `artifacts/api-server/src/lib/sentry.ts`'s `scrubEvent` deletes `event.request.data`, `cookies` and `query_string` but **never touches an exception's message** — a scrubber that looks complete and is not. Found on `POST /api/feedback` (COSM-4), where the leaked value is free text a user was explicitly invited to write candidly; the row itself stays anonymous, so this leaks content, not identity. The fix is a `catch` with **no error binding**, so the original cannot be rethrown, logged, or passed to `next()` — `catch { res.status(500).json({ error: "…" }); return; }`. Prove it red first: without the guard the test receives `app.ts`'s generic `{error:"Internal server error"}` instead of the route's own 500, which is what demonstrates the escape path is real. **This applies to every existing unwrapped drizzle call that handles user input, not just new ones** — the existing routes have never been audited for it.
- **`spawnSync` is gone (G3.1).** Solve is now async via `solver/jobRunner.ts`'s worker pool (`spawn`, not `spawnSync`) — do not reintroduce blocking sync child-process calls on the request path. One intentional exception: `__tests__/resultEnvelope.test.ts` (from G2.1) still uses `spawnSync` purely as test-invocation convenience to validate solve.py's raw envelope shape directly — it's not part of the request path, so it's out of scope for the "zero spawnSync" DoD that governed the production code.
- **`solve.py` never throws — but the wrapper's handling of a failure changed with Bundle A (Option A).** solve.py still degrades every crash/timeout/unparseable-output into a *structured* result, but it no longer emits a `{status:"error"}` result envelope: A3 routes failures over **fd3 as a structured `SolverProcessMessage` failure** (success-envelope XOR failure). And `jobRunner.ts` no longer caches/publishes an error as a result — an error-shaped outcome is now a **FAILED job**: no `result_cache` write, no `scenarios.result` publication, and a public `errorCode`∈{SOLVE_FAILED,TIMEOUT} + permanent `errorMessage` (never the raw diagnostic). This **killed the old cache-poisoning bug** (a dataset/dispatch failure used to be cached under the inputs hash *and* published as `"scenario solve completed"`, replayed for every later identical solve). Do NOT reintroduce a `status:"error"` result envelope or cache/publish a failure — the truthful contract is: success → cache+publish; infeasible/unbounded/no_solution → truthful published result; execution failure → failed job, nothing cached, nothing published. (Solver-wrapper "never throws" itself still holds — it degrades, it just degrades to a *failed job*, not a cached error result.)
- The reference-distances endpoint (`GET /models/:id/reference-distances`, Bundle 2.2/B3) is **model-scoped and immutable**, NOT scenario-scoped: base distances are geographic, status-independent, ownerless dataset data (the third field of what `/dataset` already serves model-scoped). It returns the COMPLETE base×base matrix (5200 pairs for p-median-us) unfiltered; the frontend (`DistancesTab`) filters the *view* against live `localInputs` (hiding inactive-warehouse / excluded-customer rows). Do not add server-side status filtering or make it scenario-scoped — status is a pure view concern, and scenario-scoping would forfeit the immutable per-model cache + invite the very server-side filtering that model-scoping avoids. It sets its own explicit `ETag` (global `app.set("etag", false)` disables Express's) + `Cache-Control: public, max-age=0, must-revalidate`, and is gated by `capabilities.supportsReferenceDistances` (p-median-us only so far; the frontend query is `enabled`-guarded so unsupported models fire no request).
- The login rate limiter (`routes/auth.ts`, 10 attempts/min/IP, in-memory `Map`) never resets on its own between test runs within one process. Any test file that logs in more than ~10 times (e.g. `routes.test.ts`'s per-test `loginAs()` helper) must call the test-only `resetLoginRateLimiterForTests()` export in `beforeEach`, or later logins in the same file silently start 429ing.
- **A unit migration must convert EVERY unit-bearing value in a persisted blob, not just the obvious scalars.** The `inputs` jsonb carries unit-bearing distances well past its named scalar thresholds: `distanceOverrides[].distance` is raw canonical distance that `services/precheck.ts` overlays **directly onto the base matrix**, and for an *added* entity it is the only record of that distance anywhere (`precheck.ts`'s own comment states the scope — every added-entity pair lives ONLY there). Converting the scalars and `distanceBands` while leaving the overrides reinterprets every stored override in the new unit: the migration reports success, the scenario loads, it solves, and the answers are wrong with no error on any surface. Before writing a unit migration, enumerate the blob's unit-bearing leaves from the Zod schema rather than from the fields the UI happens to show. Two companion traps from the same migration: round to 2 dp and **re-validate every row against the new schema before committing** (integer rounding can turn a valid row invalid — `high=1`, `max=1.1` both round to `1` and break a strict inequality), and bump the write authority's epoch (`solveInputRevision` + `inputsUpdatedAt`, both written DB-side via `now()`, never `new Date()`) or an in-flight old-unit solve still matches the publication CAS and republishes an old-unit result under a fresh `solvedAt`, which `isStale()` then reads as freshly correct.
- **A validation error's TEXT has exactly one producer — format it there, not at each consumer — and never let `ZodError.message` reach a client, because it *is* the JSON-stringified issue array.** Every input-validation 422 in this system used to carry a raw Zod dump (`[{"code":"too_small","minimum":0,…,"path":["avgServiceDistCapMi"]}]`) for one reason: `registry/modelRegistry.ts`'s `validateInputs` returned `result.error.message`. That is the **sole** producer of the string, so replacing it with `validation/formatInputIssues.ts` fixed create, update, clone, the import/apply path and the bands PATCH in a single line — no `openapi.yaml` change, no regenerated client, no per-route formatting. Resist the instinct to format at the route or in the UI: N consumers formatting one producer's output is how the three divergent client surfaces in `artifacts/studio/CLAUDE.md` came to exist. Two rules for the label table (`INPUT_FIELD_LABELS`, keyed on an issue's **first** path segment): it is a label table, **not** logic — validation rules stay single-sourced in the Zod schemas; and **its coverage test must iterate every `properties` key, not just `required[]`**, because the two sets do not meet. A non-required field with no label falls through a `required[]`-keyed guard and a labels-name-real-fields guard alike — that gap leaked 8 real field names across three models (`"addedMines row 1 must be greater than 0."`) past two rounds of review. The `Unknown model_id: …` branch is deliberately NOT routed through the formatter: it is already a sentence and not an issue list.
- **A server-derived field needs its derivation on EVERY write path — create, clone and update are three sites, and a strip on the client side is a fourth.** A derivation placed only on the update path either 422s every create (if the write guard refuses client-authored values) or persists nothing. Both halves bit for real in CH4O: `deriveServerOwnedInputs` had to run at all three write sites, and separately the client-side strip of the derived field was applied only to the CREATE default — but `buildWholeInputPayload()` spreads `localInputs` seeded from the persisted row, which always carries the derived field, so **every save of every affected scenario would have 422'd**. Grep for the field's writers, not its readers, and remember the persisted row is itself an input to the next save.
