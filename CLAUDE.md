# CLAUDE.md — Network Optimization Studio

Educational supply-chain network design tool. Students configure facility-location scenarios (p-median, transportation LP), solve them with a real ILP solver (PuLP/CBC), and compare results. Datasets and expected answers come from Watson et al., *Supply Chain Network Design* (Ch. 3 & 5).

Active work is governed by `IMPLEMENTATION_PLAN.md` (task IDs like A2.1, D5.1) with scope defined in `PRD-network-optimization-studio-v2.md`. When executing a task, follow the plan's per-task file lists, tests, and Definition of Done. Section 0 of the plan is the operating contract — read it first.

## Architecture (30 seconds)

pnpm monorepo. Contract-first: `lib/api-spec/openapi.yaml` is the single source of truth for the API; Orval generates the Zod validators and React Query client from it.


Solve path: frontend PATCHes inputs onto the scenario row → `POST /scenarios/:id/solve` (empty body; **DB row is the source of truth**) → route builds `SolveInput` → `pmedian.ts` pipes JSON via stdin to `python3 solve.py` (`spawnSync`, blocking) → PuLP/CBC solves → JSON on stdout → result cached as JSONB on the scenario row → response → React Query renders. The cached JSONB is what the Compare feature reads.

## Hard rules

1. **Never edit generated code.** Anything under `lib/api-zod/src/generated/` or `lib/api-client-react/src/generated/` comes from codegen. To change API shapes: edit `lib/api-spec/openapi.yaml`, re-run Orval (config: `lib/api-spec/orval.config.ts`), commit spec + regenerated output together.
2. **`e2e_accuracy.py` is sacred.** `artifacts/api-server/src/solver/tests/e2e_accuracy.py` validates solver output against the textbook's published answers. It must pass unmodified after every change. If your change breaks it, your change is wrong — do not adjust the expected values without explicit human approval.
3. **Schema changes that add NOT NULL columns to populated tables** must use the two-step protocol (add nullable → backfill → enforce NOT NULL), because `drizzle-kit push` has no migration history.
4. **One task = one commit.** Message format: `[<task-id>] <imperative summary>` (e.g. `[A2.1] add user_id ownership to scenarios`). Regenerated codegen output goes in the same commit as its spec change.
5. **Ownership filtering is security-critical.** Every scenario query must filter by the authenticated `user_id`; non-owned resources return **404** (never 403 — avoid ID enumeration). Any new scenario-scoped endpoint inherits this.
6. **Solver changes enter as data, not branches.** Business rules (forced-open, inactive, demand overrides, capacities) become variable bounds or coefficient changes in the PuLP model — never new if/else code paths in `solve.py`.
7. **Don't touch** `attached_assets/` (textbook source material) or Replit deploy files (`.replit`, `replit.md`, `push-to-github.mjs`) unless a plan task explicitly says so.
8. When the plan conflicts with the repo's actual state, trust the repo, make the smallest correct fix, and note the deviation in the commit body. If a genuinely ambiguous product decision arises, stop and ask — don't guess.
9. **Never write historical narrative into this file.** What landed — task/bundle entries, commit SHAs, gate counts, review verdicts, per-task deviations, phase completions — goes in **[`docs/CHANGELOG-implementation.md`](docs/CHANGELOG-implementation.md)** (append at the bottom, most recent last), in the **same commit** as the work it describes. `CLAUDE.md` may carry only a hyperlink to that doc, never a copy or a summary of an entry. Same rule for any other long-form record: write the content in its own doc under `docs/` and link it. The only things that belong *inline* here are durable, still-true operating knowledge — architecture, commands, hard rules, standing process, environment facts, and Gotchas. If an entry contains a durable lesson (a new bug class, a trap, a standing rule), put the **full entry in the changelog** and lift only the distilled rule into `## Gotchas` or `## Hard rules` — or, when the rule is scoped to one subsystem, into that directory's `CLAUDE.md` (Render/deploy rules: the `render-ops` skill).
10. **Never delegate to GLM in this repo** (`.claude/glm-delegation-disabled.md`) — this overrides the user-global GLM-hybrid delegation preference. Every role executes and is reviewed on named Claude models only.
11. **Overkill check first, then completeness.** For any technical implementation or discussion, the FIRST question to answer is: **is what I'm recommending overkill?**
    - **If no** — confirm explicitly that the recommended approach has no alternative that is simpler, easier to execute, and carries less technical debt.
    - **If yes** — explore, evaluate, and offer an alternative that is simpler, easier to execute, and minimizes technical debt.
    - **In either case**, the selected approach must **completely bridge the gap** between the ask and the current state — no partial or "most of the way" solutions.
    - **Ask the user clarifying questions** whenever the ask, the current state, or the gap is ambiguous — do not fill ambiguity with assumptions.
12. **Code-writing roles must run the simplicity skills — `andrej-karpathy-skills:karpathy-guidelines` AND `ponytail:ponytail` — before writing code, and `ponytail:ponytail-review` on the review pass.** Binds the **lead** (whenever it edits code itself, not only when it dispatches) and the four engineering roles: **backend-engineer, frontend-engineer, solver-engineer, devops-engineer**. Invoke both at the start of the task, not retroactively as a justification — karpathy sets the approach (think before coding, surgical changes, explicit verify step per item), ponytail's ladder picks the implementation (YAGNI → reuse what's here → stdlib → native platform → installed dependency → one line → minimum that works). Neither skill licenses cutting validation, error handling, security, or accessibility, and neither overrides a hard rule above: a ponytail-shorter path that skips the `user_id` ownership filter (#5), adds an `if/else` branch to `solve.py` (#6), or hand-edits generated code (#1) is wrong, not lazy.
    **qa-sdet is exempt from both skills** — test code is the one place where explicitness and redundancy are the point, and minimizing lines in a test is how you get a test that cannot fail. The exemption is enforced, not just asserted: ponytail is a user-scope plugin whose `SubagentStart` hook would otherwise inject its ruleset into *every* subagent, so `.claude/settings.json` sets `PONYTAIL_SUBAGENT_MATCHER` to `^(backend|frontend|solver|devops)-engineer$` and the hook injects only into those four. **Do not widen or delete that regex** — widening it re-exempts nothing and silently puts the ruleset back into qa-sdet, `Explore`, and every reviewer subagent. ## Branch discipline (standing)

**The merge-to-main pipeline. This is the governing rule; everything below elaborates it.**

1. **Every new commit lands on its own branch.** No exceptions, no "just this one" — not docs, not a typo fix, not a metrics row. `main` is never a working branch.
2. **No merge to `main` until every task in the plan is complete.** A partially-executed plan does not get integrated, however green its finished tasks are.
3. **When all tasks are done, STOP and prompt the user for approval to merge.** This is a hard stop, not a notification. Do not merge on your own judgement that the work looks finished.
4. **On approval, merge to local `main`.** This is where integration conflicts surface and get resolved — deliberately *before* the review, so the review sees the real merged result rather than a pre-merge fiction.
5. **Then run the whole-branch review**, on the merged state. It reviews what will actually ship, including anything the merge pulled in or changed.
6. **Only then push to `origin/main`.**
7. **Deploying is a SEPARATE approval. Always ask first — merge approval is not deploy approval.** No `mcp__render__trigger_deploy`, no Dashboard deploy, no env-var change on a live service, without an explicit yes for *that deploy*.

**Always invoke `superpowers:finishing-a-development-branch` when the development work is finished — at step 3, before prompting for merge approval.** "Finished" means implementation complete and the gates green; that is the appropriate time, not after the merge and not after the push. The skill owns the end-of-branch decision (merge / PR / cleanup / retire) and running it is what makes that decision deliberate rather than improvised. Invoking it does **not** grant any of the approvals above: steps 3–7 still each need their own explicit yes, and the skill's output is a recommendation to put to the user, never a licence to act.
(Recorded 2026-10-04 after the `sidebar-hamburger-rail` bundle ran the entire pipeline — gates, QA, whole-branch review, merge, push, deploy — without the skill ever being invoked. Nothing went wrong *because* of the omission, and that is the point: the steps were reconstructed by hand each time from this section, which works right up until the one time a step is forgotten, and leaves `/harness-retro` and branch retirement dangling at the end with no prompt to run them. The branch was still un-retired and the retro still unrun when the work was otherwise complete and live in production.)

**Pushing to `origin/main` is not cleanly separable from deploying, so treat the push itself as deploy-adjacent and say so when asking:**
- `nos-api` — `autoDeployTrigger: commit` (verified live via `get_service`, 2026-10-03). The old claim here — `off`, Blueprint-authoritative, "a push does not deploy it" — was wrong on both halves, and `render.yaml:20-28` already carried a dated correction saying so. **Do not re-derive this from either file; read the live service.** In practice the webhook does not fire anyway (see the `render-ops` skill), so a push arms it without starting it — which is a different fact from "a push cannot deploy it".
- `nos-studio` — Dashboard-managed static site with no suppression. A push **can** deploy it. Historically the webhook has not fired on its own for this service (see the `render-ops` skill), but that is observed unreliability, not a guarantee — never rely on it as a safety mechanism.

So a push to `main` may ship the frontend while leaving the API on the previous build. If that skew matters for the change in hand, say so when asking, and check `list_deploys` after any push to see what actually happened.

Never reorder these. Reviewing before the merge reviews code that does not exist yet; pushing before the review publishes unreviewed code. A branch that is merged locally but not yet reviewed is recoverable; a pushed one is not.

**Each step is authorised separately. "Merge" does NOT authorise a push; "push" does NOT authorise a deploy.** Approval for one step is approval for exactly that step — carry out that step, then stop and ask for the next. Do not read a single instruction as consent for the remainder of the pipeline, and do not batch steps together because they seem like one obvious unit of work.
(Recorded 2026-09-30 after the reverse: asked to "merge", I merged **and** pushed in the same action. Nothing broke — no deploy was triggered — but the push was not authorised and, unlike the merge, is not locally recoverable. The user granting step 4 is precisely when step 6 is closest and most tempting to assume.)

**Step 5a — when the review returns findings, SWITCH BACK TO THE BRANCH before fixing them.** The pipeline above is written as one pass, but a review that returns findings creates a loop: fix → re-merge → push. The fixes are a **new commit**, so rule 1 applies again and they belong on the branch, not on `main`. This is the pipeline's most dangerous moment for rule 1, because step 4 has just left HEAD on `main` and the findings arrive while it is still there — there is no natural cue to move. `git switch <branch>` carries uncommitted edits across cleanly here (the two commits hold identical content for those files), so the switch can happen before or after the edits; what matters is that the commit does not land on `main`.

**Guard the COMMIT, not only the merge.** Before any `git commit`, assert you are not on `main`:
```bash
[ "$(git rev-parse --abbrev-ref HEAD)" != "main" ] || { echo "ON MAIN — commit refused"; exit 1; }
```
(Recorded 2026-10-01. In one task-loop session the review-findings commit for `HND-B` landed directly on `main` — while the *same session* had correctly switched back for the preceding task an hour earlier, so this is not ignorance of rule 1. Five compounding causes, kept because each recurs: (1) step 4 leaves HEAD on `main` exactly when findings arrive, and the pipeline had no documented loop step — hence 5a above; (2) **the branch assertion existed but pointed the wrong way** — every merge carried `[ ... = "main" ]`, asserting *I am on main*, the exact inverse of what a commit needs, and no commit command carried any precondition at all: the step that had burned me before was hardened and its neighbour left bare; (3) ~15 verification tool calls separated the review's return from the first edit, so the branch question had been settled implicitly long before the commit; (4) **"right worktree" was conflated with "right branch"** — the worktree had been explicitly verified and is stable, but the branch inside it moves on every merge, so the verification being carried forward was of the wrong variable; (5) "same task" was treated as "same commit" — rule 1 is per-commit. Recovered because it was unpushed: `git branch -f <branch> <sha>` moved the commit, `git reset --hard <merge>` restored `main`, then a normal re-merge. Afterwards `git log --first-parent` showed merges only, i.e. history indistinguishable from having done it right — **and that is also the check**: `main`'s first-parent line should contain nothing but merge commits.)

**Never pipe a git command whose exit code gates the next step.** `git checkout main 2>&1 | tail -2 && git merge <branch>` runs the merge **even when the checkout fails**, because `&&` sees `tail`'s status, not git's. Run the state-changing command alone, read its output, then act — or at minimum assert the post-condition before depending on it (`git rev-parse --abbrev-ref HEAD`).
(Recorded 2026-10-02, ch9-tc. HEAD had been parked on another session's branch since that morning; `git checkout main` failed with `'main' is already used by worktree at .worktrees/task-loop`; the merge then ran on **that** branch and conflicted in three files. Aborted with no commit, nothing lost. Three things had to line up: piping to `tail` was a session-long habit for trimming output, harmless on read-only commands and fatal on a gating one; the two state changes were fused into one shell line to save a tool call, so no observation point existed between them; and — the part worth internalising — **the pre-merge check could not have caught it.** `git rev-parse main origin/main`, `merge-base --is-ancestor` and a clean-tree check all read main's *content*, which is readable no matter which worktree holds the branch. Availability is a different question: `git worktree list | grep "\[main\]"`, or just not masking the exit code.)

**Commit with an explicit pathspec whenever the index may hold something you did not put there.** `git commit <paths> -m …` commits only those paths and leaves the rest of the index alone; a bare `git commit` takes whatever is staged.
(Recorded 2026-10-02, ch9-tc, 13 minutes after the incident above. `git apply -3` **stages** what it applies — 3-way needs the index — so the later `git checkout -- .github/workflows/ci.yml` restored that file *from the index*, not from HEAD, and was a no-op against the intent. The subsequent `git add <other-file> && git commit` then committed the whole index, so a file the commit message explicitly said was excluded was in the commit. Caught by re-reading the commit, fixed with `git checkout HEAD~1 -- <file>` + `--amend`. Two contributing habits: `git status --short`'s staged/unstaged distinction is **column position** — `M ` is staged, ` M` is worktree — and reading the letter without the column makes staged changes invisible; and the commit message was written from intent before `git diff --cached --stat` was ever read, so the message asserted a state nobody had checked.)

**Both of the above are the same failure: asserting the state you intended instead of observing the state that exists**, at a boundary where an expectation had already formed. The verifying command was one line away in each case. Note the second happened *after* the first, in the same session: the response to incident 1 was a guard for that exact instance (`[ "$(git rev-parse --abbrev-ref HEAD)" = "main" ]`, which then worked correctly on three real merges) and no generalisation to the class — the same patch-the-instance-not-the-class mistake the 2026-10-01 entry above documents. Detection worked both times; prevention did not.

- Do not commit directly to `main` for routine bundle work or ad hoc fixes. Every feature or remediation change must land on a descriptive branch first.
- Keep a branch for each bundle or repair, and set an upstream remote at the first stable checkpoint so the work is recoverable outside the local machine.
- Protect the active worktree and branch from cleanup or deletion until its branch has been reviewed, backed up remotely, and explicitly approved for retirement.
- Read-only proof is required before any branch or worktree deletion: `git cherry main <branch>`, clean status, explicit path validation, and confirmation that no agent/session still owns the branch.
- Never use `rm -rf` for branch cleanup; use `git worktree remove <exact-path>` only after human approval.
- Never escalate a branch deletion to `git branch -D` without a second approval that cites the `git cherry` proof and the specific reason the branch is not ancestry-merged.
- Treat direct-to-main commits, stale branch backlogs, and unreviewed worktree churn as stop-and-report conditions rather than normal repo hygiene.
- Keep the operating rules in sync with the branch discipline plan and do not drift from the repo's branch lifecycle without an explicit decision.
- This section is the **in-repo policy** (documented agent discipline). Server-side enforcement — GitHub branch protection / required CI — is a **separate, human-approved infra task**, not covered here. Recurring offenders to correct: routine bundle work, Sentry/PostHog changes, and remediation itself committing straight to `main`.
- **Design docs have ONE canonical copy — edit in place, never re-sync a divergent copy.** `docs/superpowers/specs/**` + `plans/**` are canonical on `main`; a feature branch branches off **current `main`** and edits them in place. Do **not** maintain a parallel "synced" copy on another line — that guarantees add/add + content merge conflicts (2026-09-24: the A-execution line and local `main` both evolved the same 5 SCND design docs independently → ~337 diff lines to reconcile at merge; audit confirmed the divergences were superseded-earlier-phrasings, no content lost, but it was avoidable churn). **Before any merge to `main`, confirm local `main` isn't stale vs `origin/main`** (`git fetch`; `git merge-base --is-ancestor <deployed-sha> main`) — in that same incident local `main` had never merged the deployed Bundle A. ## Gotchas

**Subsystem gotchas live next to their code and auto-load when you work there** — read the one for the directory you are touching (cross-directory triggers: editing `capabilities.locked` in a `solvers/*/manifest.json` or the studio's `chapters.ts` → read the locked-model entry in `artifacts/api-server/CLAUDE.md`): `artifacts/studio/CLAUDE.md`, `artifacts/studio/e2e/CLAUDE.md`, `artifacts/api-server/CLAUDE.md`, `artifacts/api-server/src/solver/CLAUDE.md`, `lib/db/CLAUDE.md`. Render/deploy/production-DB gotchas are in the `render-ops` skill — invoke it before any deploy, any Render MCP call, or any production Postgres work. Two of its rules must never be missed: **the Render Postgres role pair (`nos_postgres_user` owning everything) is the design — never `DROP`/`REASSIGN` it**; and **treat a push to `main` as deploy-adjacent** — the commit webhook has not been observed to fire, but both services are armed (Branch discipline above), so it is not a safety mechanism; deploy only with explicit approval, then check `list_deploys`.

- **`Agent` tool `isolation: "worktree"` is racy under simultaneous launch — some agents silently land in the SHARED controller checkout instead of a private worktree.** In the workspace-fixups bundle, 4 agents were dispatched in one message with `isolation: "worktree"`; T2 and T8 got real private worktrees, but T1 and T3 both fell through to the controller's own `jade-ch9` dir — T3's `git checkout -B` there switched the shared checkout's branch mid-run while T1 was also in it, exactly the shared-index class the Bundle 3 book-cover incident documented, but worse (concurrent HEAD moves). The base guard (`git merge-base --is-ancestor <tip> HEAD`) is what caught it — T1 refused to proceed and reported the collision instead of corrupting history; no bad work landed. **Fix/standing rule for agent-team dispatch: do NOT rely on `isolation: "worktree"` for parallel agents. Pre-create a dedicated locked worktree per task yourself (`git worktree add --lock <path> -b <task>-work <base-sha>`), dispatch WITHOUT `isolation`, and make each agent's FIRST Bash command `cd <that exact path>` + a `git rev-parse --abbrev-ref HEAD` sanity check (must equal `<task>-work`, else STOP).** The controller then cherry-picks each task's commit onto the bundle branch (shared object DB makes every agent commit reachable) and re-gates. This ran the remaining ~8 agents collision-free. Keep the base guard regardless — it is the backstop that turns a worktree mishap into a clean stop rather than a corrupted branch.
- **A UI-changing bundle silently breaks PRIOR bundles' Playwright e2e specs that are still in `e2e:gate` — rewrite the sibling specs BEFORE merge, don't just add your own.** Recurring `spec_gap` class (bundle 6.1's `b43fe1f`, the OBS-3-audit block, and workspace-fixups-2 all hit it): when a bundle removes/renames a testid, deletes a component (e.g. `JadeBandEditor` → `jade-band-slot-*` gone), or changes a visible-string contract (e.g. band-filter labels now start `Band N:`), every prior `e2e/*.spec.ts` that hard-codes the old shape fails — and none are `@flaky`-tagged, so a full `pnpm e2e:gate` run breaks even though every unit/RTL suite is green. The unit gate does NOT catch this (Playwright specs aren't in `pnpm --filter studio test`). **Standing step: at whole-branch-review/QA time, grep the `e2e/` dir for any testid/string your bundle changed and rewrite those sibling specs to the new UI (the QA agent, with local servers already up, is the natural owner), running them green before merge.** The proposed gate (`pnpm e2e:gate in CI`) is still not enabled (no CI browser/app/seed infra), so this is a manual discipline until then.
- **An agent-team subagent can stall on a stream/watchdog timeout (`no progress for 600s`) with its uncommitted work INTACT in its worktree — resume it via `SendMessage`, do NOT re-dispatch a fresh agent.** Hit once in workspace-fixups-2's INT task (the largest task): the watchdog fired mid-test-rewrite, status `failed`, but `git status` in its worktree showed all the real source changes + partial test edits still present (nothing committed). A fresh `Agent` call would start from the base and redo everything; `SendMessage` to the same agentId resumes it from its transcript, and it finishes from where it stalled. First inspect the worktree read-only (`git status --short`, `git log -1`) to confirm the work is there and uncommitted, then send a precise "finish these remaining items + gate + commit" message.

- **A change crossing a layer boundary is ONE commit.** Schema, solver, payload builder, test fixtures and frontend defaults speak one contract; splitting a contract change across commits guarantees a broken intermediate commit, so slice tasks by contract, never by layer. Two corollaries: **remove consumers before producers** (frontend stops reading a field → server stops serving it → the field leaves the OpenAPI contract, each step green), and **a new closed-union error code is a change in three places** — the TS union, the OpenAPI enum, and the regenerated client — so it is one task, not three.
- **A real-Postgres test that inserts a `queued` solve_job can have that row CLAIMED by a dispatcher in ANOTHER session's concurrent vitest run.** Every session on this machine shares one local `nos_dev`, and the api-server suite's own dispatcher tests (`dispatcherRecovery`, `jobRunnerDispatcher`) start real dispatchers. Symptom: a job flips `queued` → `running` between two back-to-back awaits in a file that never starts a dispatcher. This is one level worse than the load-flake class below — another session's dispatcher **mutates** this session's rows, it does not merely slow them down, so no amount of re-running in isolation explains it while the other session is live. Mitigation: assert "either active status" rather than exactly `queued` when what the test actually needs is a row the active-job index predicate matches.

- **The studio vitest suite flakes under load from ANOTHER SESSION'S test run, and the failures name files your branch never touched.** Observed 2026-09-29 on `ch5-delivery`: two consecutive full `pnpm --filter studio test` runs reported 14 and then 36 failures across `DistancesTab`, `JadeDistancesTab`, `JadeFlowsTab`, `Studio`, `Workspace`, `CustomerTable` and `ImportDialog`, every one shaped `Test timed out in 5000ms`. This is the same contention class already documented for api-server and Playwright, but it had never been recorded for studio vitest — and it is more misleading here, because the failing files look like a broad regression in shared components rather than a flake. **Before trusting any full studio-suite result as a gate — especially the pre-merge gate — check for concurrent runs and require 0.** Parallel agent worktrees are now the normal way this repo runs, so assume contention rather than a regression when unrelated files time out together.

  Use `ps aux | grep "[v]itest" | grep -vc "zsh -c"`, **not** `ps aux | grep -c "[v]itest"`. The bare count also matches the agent's own `zsh -c` wrapper — whose command line contains the pattern text — so it reports 2 when the real answer is 0, and "require 0" becomes unsatisfiable. Confirm with `ps aux | grep "[v]itest" | grep -v "zsh -c"` and read the actual command lines before concluding anything; a count you cannot see the rows behind is the same class of non-discriminating check as everything else on this list.

  **Never chain that check with `&&` — `grep -c` exits 1 when the count is 0, so the success case is the one that short-circuits.** `grep -vc "zsh -c" && pnpm --filter api-server test` silently skips the suite precisely when the machine IS quiet, and prints the all-clear while doing it (hit 2026-10-09, CH4O-13). Assign it and test it: `cnt=$(… | wc -l | tr -d ' '); [ "$cnt" = "0" ] || exit 1`. Same family as the `git checkout main | tail -2 && git merge` incident in Branch discipline — a guard whose exit code is read from the wrong command is worse than no guard, because it reports success.

- **Bumping an emitted version constant and updating the contract that publishes it are ONE change — and an empty `rows: []` fixture cannot witness a row-shape change.** CH4O shipped `COST_SUMMARY_TEMPLATE_VERSION = 4` plus three new export columns while `openapi.yaml` still said `templateVersion: { enum: [3] }` with the original 8 `required` row properties, so the Orval output carried the stale shape (`zod.literal(3)`; `NUMBER_3: 3`, making `4` unassignable to the envelope type the server ships) and the API violated its own published contract — hard rule #1, found only by the whole-branch review. The gate could not catch it because the **only** consumer of that schema in the repo validated a hand-built `{ templateVersion: 3, entity: "costSummary", rows: [] }`: the literal froze the version it was supposed to track, and the empty array made the three added properties unobservable. Two rules follow. **Pin a contract test to the constant, never to a literal copy of its current value** — a test that hardcodes the number it is guarding converts a version bump into a silent contract drift. And **a schema test needs at least one populated row, ideally one the production builder actually returned**, because an empty collection satisfies every row schema that has ever existed. This is the repo's hand-authored-fixture hazard (below) aimed squarely at the one artefact whose entire purpose is to announce that a shape changed.
- **A test suite must never be able to execute a production data migration — scope the migration function, do not rely on pointing it at the right database.** `migrateAllIntegration.test.ts` called the unfiltered `migrateAll(db)`, which selects *every* row for its model in the connected database, rewrites `inputs`, nulls `result`/`solved_at`/`result_run_id` and deletes that model's entire `result_cache`. Because this repo passes `DATABASE_URL` **inline per command**, a single copy-pasted production connection string would have destroyed production data from a routine `pnpm --filter api-server test` — with none of the runbook's mandatory backup, and unrecoverable without a snapshot. The runbook's "do not run this against production" is a human-process control, and this test quietly turned it into something the normal verification gate does. Give any destructive migration an optional id filter and have its tests pass only their own fixture ids; keep the unfiltered full-scan behaviour for the production entry point alone. Note the shape of the near-miss: the test file's own teardown comment reasoned carefully about not over-deleting `result_cache` two lines below a call that deleted all of it — **local care inside a function whose blast radius is global is not a safeguard.**
