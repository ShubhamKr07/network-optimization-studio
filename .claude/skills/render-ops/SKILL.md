# Render operations — gotchas

Moved out of the root `CLAUDE.md`. Deploying still needs its own explicit approval (Branch discipline step 7).

- **Render's Postgres uses a login-shim role pair. `nos_postgres_user` owning everything is the DESIGN, not drift — do not "clean it up".** `nos_postgres_user2` is the credential Render hands out (external URL, `databaseUser`, and the `fromDatabase` `connectionString` all use it), but Render also sets `ALTER ROLE nos_postgres_user2 SET role = nos_postgres_user`, so every connection authenticates as `user2` and then immediately becomes the owner role. Hence `session_user=nos_postgres_user2` while `current_user=nos_postgres_user`, and hence all three things that look like leftover migration debris: the old role owns all 21 public objects **and** the `public` schema; the tables carry `<no explicit ACL>` (only an owner needs one); and `user2` is a member of the old role (required for the auto `SET ROLE`). Confirm in one query: `SELECT r.rolname, s.setconfig FROM pg_db_role_setting s LEFT JOIN pg_roles r ON r.oid=s.setrole;`.
  **Why retiring the old role is wrong, not merely risky** (investigated 2026-09-30, closed won't-do): `DROP ROLE` breaks every `user2` connection, because `user2`'s `role=` default points at the dropped role. And `REASSIGN OWNED … TO nos_postgres_user2` *creates* the split it appears to fix — new objects keep landing on the old role via that same default, so ownership genuinely ends up spread across two roles. A superficially "half-migrated" database here is actually in its intended, coherent state.
  Two real consequences that are NOT invalidated by the above: (1) a leaked password for `nos_postgres_user` is a genuine exposure — it grants direct owner-level login, bypassing the shim — so rotate it, and note that `ALTER ROLE … WITH PASSWORD` on a Render-managed role desyncs anything Render stores for it (recoverable via a Dashboard reset); (2) the `DEFAULT PRIVILEGES` granting future objects to `nos_postgres_user` are owned by the `postgres` superuser and unchangeable by either role — under this model that is correct, not a bug.

- **Creating a Render resource via MCP instead of a Blueprint apply silently loses Blueprint-only config.** `create_web_service`/`create_static_site` (the `render` MCP server) have narrower parameter schemas than `render.yaml`'s full Blueprint schema — e.g. `create_static_site` has no `routes`/rewrite field at all. `nos-studio` was created this way (forced because `nos-api` needed Docker, which `create_web_service` explicitly can't do, breaking the clean all-Blueprint path) and shipped with zero SPA-fallback rewrite: root `/` worked, every client-side route (`/chapter-3`, `/compare`, ...) 404'd in production until a real user hit it post-deploy. **Before creating any Render resource type for the first time via MCP, read that type's own `render-<type>` skill first** (`render-static-sites`, `render-web-services`, etc.) specifically for Blueprint-only fields the MCP tool's schema won't surface — don't trust the MCP tool's parameter list to be the complete requirements picture. Fixed via a one-time manual Dashboard edit (Settings → Redirects/Rewrites, `/*` → `/index.html`) plus syncing the same rewrite into `render.yaml` so the Blueprint stays accurate for next time. See `docs/superpowers/plans/2026-07-24-render-migration.md`'s R0.9 retrospective for the full incident.
- **A "frontend loads" check that only hits `/` cannot catch a missing SPA-fallback rewrite.** Root always has a matching static file regardless of rewrite config; only a nested client-side route actually exercises it. Any future deploy-verification checklist for a static SPA needs at least one non-root route check.
- **`query_render_postgres` is read-only by design (it wraps every query in a read-only transaction), and allowlisting an agent's egress IP does nothing for it.** The hosted MCP server connects from its OWN address (observed: `35.227.164.209`, Google Cloud), not from this machine — so adding your local IP to the database's allowlist enables `psql` from here and changes nothing for the MCP tool. "I have database access via MCP" and "I can run DDL" are different claims; production schema changes need `psql` from a machine on the allowlist with a connection string. (Recorded 2026-10-04, creating the `feedback` table: two sessions spent a round trip on this before the error naming the Google Cloud address made it obvious.)
